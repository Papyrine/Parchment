# Contributing to Parchment

Architecture, design decisions, and non-obvious gotchas for people working on Parchment itself. User-facing feature docs, PARCH diagnostic codes, the `[ParchmentModel]` placement rationale, model binding limitations, and the determinism guarantee live in `readme.md` — link there rather than restating.

## Build and test

Two solutions: `src/` (library + source generator + tests + sample model) and `IntegrationTests/` (consumes the packed nuget end-to-end).

```bash
dotnet build src --configuration Release -p:IsPackable=false
dotnet build IntegrationTests --configuration Release   # requires src to be built/packed first — Parchment is a PackageReference, not a ProjectReference
```

Tests use **TUnit** (not NUnit/xUnit). Each test project is `OutputType=Exe` with `TestingPlatformDotnetTestSupport=true` — run via `dotnet run`, not `dotnet test`:

```bash
dotnet run --project src/Parchment.Tests --configuration Release -p:IsPackable=false
dotnet run --project src/Parchment.SourceGenerator.Tests --configuration Release -p:IsPackable=false
dotnet run --project IntegrationTests/IntegrationTests --configuration Release

# Single class, then a single test (TUnit tree-node filter: /assembly/namespace/class/test)
dotnet run --project src/Parchment.Tests --configuration Release -p:IsPackable=false -- --treenode-filter "/*/*/HtmlInlineRendererTests/*"
dotnet run --project src/Parchment.Tests --configuration Release -p:IsPackable=false -- --treenode-filter "/*/*/HtmlInlineRendererTests/ITagAppliesItalic"
```

TUnit narrows with `--treenode-filter`; the VSTest `--filter "FullyQualifiedName~..."` form is not understood. A local `Release` build of anything under `src` needs `-p:IsPackable=false`: packable projects bundle SponsorCheck, which fetches from GitHub and fails the build with `SC100` (HTTP 401) wherever the CI credentials are absent.

Snapshots: **Verify.TUnit + Verify.OpenXml + Morph.Skia**. Failed test writes `*.received.*`; accept by renaming to `*.verified.*`. PNG page renders fire on `net10.0` automatically when `Morph.Skia` is referenced. The `*.verified.png` files are byte-for-byte outputs of Morph's deterministic renderer, so they are coupled to the exact `Morph.Skia` version pinned in `src/Directory.Packages.props`: bumping it changes rendered layout, requiring a re-accept of the PNG snapshots plus a regeneration of the scenario `input.png` files via the `[Explicit]` `ScenarioInputRenderer` test (see "Scenario directories"). PNG-only failures with equal `.docx`/`.txt` snapshots mean the rasterizer changed, not Parchment.

CI: `.github/workflows/build.yml` (GitHub Actions, windows-latest). Build first installs every TTF/OTF in `src/Fonts/` into the Windows fonts dir, validating each via `System.Drawing.Text.PrivateFontCollection` so a CRLF-mangled font fails the build instead of producing "font not found" at test time. Morph >= 1.1.4 embeds the Aptos 400/700 regular + italic faces inside `Morph.dll`, so PNG renders do not depend on that install for those faces; it still covers faces Morph does not embed (`Aptos_Display_700.ttf`).

## Architecture

Parchment combines a .NET data model with one of two template formats and produces a `.docx`. User-facing overview of the two modes is in `readme.md` → "Two modes". The two flows share token scanning, the Fluid singletons, the markdown renderer, and the snapshot pipeline, but execute very differently.

### Flow A — Docx template (`RegisterDocxTemplate<T>` / `Render`)

Template is a real `.docx` containing liquid tokens scattered across paragraphs. Handing the whole file to Fluid is not viable — body paragraphs contain Word run-level formatting that text-based liquid would destroy. Instead:

1. **Token scanner** (`Tokens/TokenScanner.cs`, `Word/ParagraphText.cs`) — walks paragraphs in `MainDocumentPart`, every `HeaderPart`, `FooterPart`, `FootnotesPart`, `EndnotesPart`. For each paragraph builds flat `InnerText` + a `RunMap` (offset → `<w:t>` element), regex-scans for `{{ ... }}` and `{% ... %}`, classifies as `Static` / `Substitution` / `Block`. A paragraph's text is only the `<w:t>` elements whose nearest paragraph ancestor is that paragraph (`ParagraphText.Texts`): a text box anchored in a run holds paragraphs of its own, and those are scanned and substituted as separate paragraphs. `ParagraphSplicer`, `EditableSplicer` and the source generator's `DocxArchiveReader` enumerate the same way, so token offsets agree everywhere; a `Descendants<Text>()` walk over a host paragraph would double-count the text box content. **Lockstep**: `FormFields.ToTokens` rewrites each `FORMTEXT` field into a `{{ Name }}` run before this scan, and the generator cannot rewrite the document, so `DocxArchiveReader.FindFormFields` applies the same rule while reading — the token text in place of the run opening the field, every other run of the field skipped. Change which fields convert in both. Tests: `FormFieldTests` (runtime) and `FormFieldGeneratorTests` (SG) build the same field shapes under the same test names. Inline wrappers (`w:hyperlink`, `w:ins`, `w:moveTo`, `w:fldSimple`, `w:customXml`, `w:dir`, `w:bdo`, inline `w:sdt`) are descended through like any other element. `w:smartTag` is the exception that needs help: the Open XML SDK has no class for it, so it and its whole subtree load as `OpenXmlUnknownElement` and no `Run` or `Text` is found inside. `ParagraphText.Elements` calls `SmartTags.Retype` on reaching one, which re-reads each child as a paragraph child and swaps the typed element in, leaving the smart tag itself in place. The retyping does not survive a save (a render works on a copy of a parse of the snapshot, see `ParsedParts` under step 5), which is why it happens in the walk and not once at registration; a walk over a paragraph that bypasses `ParagraphText.Elements` does not see into a smart tag. The generator reads raw xml by element name and needs no equivalent.
2. **Anchor bookmarks** (`Word/Anchors.cs`) — every token-bearing paragraph gets an invisible `<w:bookmarkStart w:name="parchment-anchor-{guid}"/>` at scan time. These survive byte-stream cloning so render-time can look up host paragraphs by name. Stripped before save.
3. **Scope tree** (`Tokens/RangeNode.cs`, `ScopeTreeBuilder.cs`) — recursive walk groups block-tag paragraphs with their bodies into `LoopNode` / `IfNode` / `IfBranch`, with non-block paragraphs as `SubstitutionNode` / `StaticNode` leaves. Block tags MUST sit alone in their paragraph; mixed inline text + block tag is rejected at registration (PARCH005 in SG docx flow). The tag paragraphs of one block MUST also share a parent element (`RequireSameContainer`; PARCH028 in SG docx flow): tags are paired by document order, but the runner reaches a block's content by walking siblings between them, so a tag in another cell is never reached. Each part is scanned once: the tree the validators accept is the tree stored on the registered template, in both flows (`RegisterDocxTemplate`, `PrepareStyleSource`). A tree refers to its paragraphs only by anchor name, so that holds only while the package is saved from the same open document the scan wrote its anchors into — a step that reopens or re-clones the package between the scan and the save has to rebuild the trees from the new anchors. A token-free paragraph never reaches the tree. An anchor the input arrived with (a previously registered or half-processed document reused as a template or style source) is removed by `Anchors.StripArrived` before the scan, in every part both flows read, and the removal is baked into the registered bytes; in `PrepareStyleSource` it counts as a change, so a token-free style source is rewritten for it. Tests: `ArrivedAnchorTests`.
4. **Reference validator** (`TemplateStore.cs::ReferenceValidator`) — walks scope tree, runs `ModelValidator` against `TModel` via reflection. Loop variables introduce scoped bindings (`item: ElementType`) into a `Dictionary<string, Type>` that nested loops/conditionals inherit. Throws `ParchmentRegistrationException` on first missing member.
5. **Render** (`Tokens/ScopeTreeRunner.cs`, `RegisteredDocxTemplate.cs`) — clones canonical bytes, builds anchor → paragraph map, walks the cached scope tree:
   - **Substitutions**: get parsed `FluidTemplate`, pull `OutputStatement.Expression`, call `Expression.EvaluateAsync(context)`. If result's `ToObjectValue()` is a `TokenValue`, queue structural replacement; else apply in-paragraph text substitution. In-paragraph substitutions applied **in reverse offset order** so earlier offsets stay valid. A string assigned to a `TokenValue` member (a `TextToken`) is never such a result: a value converter in `SharedFluid.BuildOptions` hands Fluid the string, so filters, conditions and the substitution see what a `string` member would give, and a null string stays nil.
   - **Loops**: `LoopNode.LoopSource.EvaluateAsync(context).Enumerate(context)` (Fluid's own `Expression`, not a wrapped template). For each item, deep-clone body elements, rewrite anchor-bookmark names to fresh per-iteration GUIDs, recursively process the clones with loop variable bound in scope. `LoopNode.Limit` / `Offset` / `Reversed` carry the tag's modifiers off the parsed `ForStatement`, and `ApplyLoopModifiersAsync` repeats the arithmetic of Fluid's `ForStatement.WriteToAsync` so both flows window a loop the same way.
   - **Conditionals**: `IfBranch.Condition.EvaluateAsync(context).ToBooleanValue()`. Chosen branch processed in place; non-chosen branch paragraphs removed.
   - Structural replacements applied last, top-down, via `parent.InsertAfter` + `host.Remove`.
   - **Failures** (`Errors/RenderFailure.cs`): every catch in a render is `catch (Exception e) when (RenderFailure.ShouldWrap(e))` followed by `RenderFailure.Wrap`. The catches nest — token, block tag, part, template, in both flows — and the filter is what keeps that safe: it lets a `ParchmentException` through, so the innermost catch's context is the one reported, and an `OperationCanceledException`, so cancellation stays recognisable. A new catch on the render path has to use the same filter. The markdown body is one Fluid call, so a failure inside it has the template name and nothing finer. Two things sit outside the outermost catch because they are the caller's arguments rather than the template's: `DocumentPropertiesWriter.Apply`, whose `ArgumentException` is tested for, and the copy to the output stream.
   - Word merges adjacent `w:tbl` siblings into one table, and a render brings together tables the template kept apart: a token produces one beside another, a tag paragraph, a branch that was not chosen or a token that produced nothing was all that stood between two, a loop writes one copy of a table after another. So every table that gets a different block before it is recorded in a list shared with the loop and if-branch runners — a table a structural replacement produces and the table after its last block, the table after any block taken out through `ScopeTreeRunner.Remove`, the table a loop iteration opens with — and the root runner's `SeparateTables` runs once the tag paragraphs are gone, reading each container that holds a recorded table once and inserting an empty paragraph before a recorded table that directly follows another table. Tables that are adjacent in the template itself are never recorded and are left alone, inside each loop iteration as well. A new site that removes or inserts a block has to go through `Remove` or `RecordTableAfter`. Tests: `StaticTableSeparationTests`, and the `ExcelsiorTableTests` cases for produced tables.
   - **Block removals are queued.** `OpenXmlElement.Remove` walks every sibling ahead of the element, so a long body of block tags paid the length of the body for each paragraph dropped. `ScopeTreeRunner.Remove` only adds the block to a set, and `FlushRemovals` unlinks the set in one pass per parent (a few are removed one by one). A queued block is still linked: its `Parent` is not null and its siblings still reach it. So code in the runner that asks whether a block is gone uses `IsRemoved`, code that reads the siblings of a block skips the set as `RecordTableAfter` does, and anything that hands a paragraph to code outside the runner calls `FlushAllRemovals` first — a `MutateToken` or `OpenXmlToken` delegate, and `EditableHtmlBuilder`, which asks whether the host is alone in its cell. An if-branch runner shares the set of the runner that created it and leaves the flush to that runner; a loop runner has its own and `ApplyStructural` flushes it for each iteration, before the scratch body is moved into the document. The root runner's `ApplyStructural` flushes before `SettleSectionBreaks`, `SeparateTables` and `ApplySectionBreaks`, all of which read neighbours. Tests: `BatchedBlockRemovalTests`.
   - **`[SECTION]` in a markdown value**: a `MarkdownToken` goes through `MarkdownRendering.Render`, whose walk writes a `[SECTION]` marker as a paragraph carrying only what the marker declared (see Flow B, step 3). The template's own section breaks look the same from outside, so the runner cannot find markers by scanning the way the markdown flow does: `RenderTokenValue` reports `mayHoldSections`, `SectionBreaks.Collect` records the marker paragraphs in a list shared with the loop and if-branch runners, and the root runner's `ApplySectionBreaks` hands them to `SectionBreaks.ApplyInPart` once every iteration is in its final place. Each run of markers is derived from the next `w:sectPr` in document order — a template paragraph's or the body's last — which is rewritten in place to what the run's last marker declared. A non-body root, a marker that did not end up a direct child of the body, and a body with no `w:sectPr` after the marker all throw. `ParagraphSplicer.Split` clones what it is given, so the non-solo path collects from the split result rather than from what was rendered; and a value that is only a marker skips the inline splice, which would drop the paragraph properties that are the break. `RegisteredMarkdownTemplate.RenderNonBodyParts` makes the same call, where it can only reject. Tests: `MarkdownValueSectionBreakTests`.
   - **Render reads only the parts that carry tokens.** Touching a part's typed root makes the SDK parse the part and write it back out on save, so `DocxCloner.EnumerateParts` takes the set of part uris that have a `PartScopeTree` and both flows pass it at render; every other header, footer and notes part stays as the bytes cloned from the snapshot. Three things make "no scope tree" mean "nothing to do", and all three have to keep holding. Registration removes every anchor the input arrived with (`Anchors.StripArrived`) and the scan anchors token paragraphs only, so a part without a tree has nothing for `Anchors.StripAll`. A `LineBreaks.Marker` only arrives through a substitution. And a cell without a closing paragraph in such a part can only be the template's own, which registration closes (see "Table cells" below). A new per-part render pass that has work in a token-free part breaks this: do that work at registration, or give the part a tree. The output is byte-identical either way, because the snapshot is itself SDK-serialised for every one of these parts (registration reads them all) and that serialisation is stable when repeated. Tests: `TokenFreePartTests`.
   - **Token parts are parsed once and cloned per render** (`Word/ParsedParts.cs`). Parsing the token-bearing parts from xml was a quarter to a third of a render, and the result is the same every time. The first render of a template reads them from the snapshot, keeps the children of each root, and saves a second copy of the package with those roots emptied; every render opens that copy and appends a deep clone of the kept children to each root (`Fill`) before anything else touches it. The kept tree is shared by concurrent renders without a lock, so it is never mutated after `ParsedParts.Read` returns: a render is only ever handed clones, and `Read` walks every element first, because an element the Open XML SDK holds as unparsed xml parses itself on first access, which a clone would otherwise trigger on the shared copy. A new consumer that needs the template's content has to clone as well, never read or keep a reference into the kept elements. The tree is a parse of the saved snapshot and not the document registration scanned, because that is what a render has always started from — taking the registration tree instead would carry over what does not survive a save (a retyped `w:smartTag`, an annotation) and change the output. A scope tree names its paragraphs by anchor, never by reference, which is what lets it work against any clone. Tests: `ParsedPartsTests`.
   - **Line breaks** (`Word/LineBreaks.cs`): a newline in a substituted value has to become a `w:br`, and splitting a `w:t` mid-walk would invalidate the offsets the reverse-order substitutions depend on. So `ParagraphText.Replace` parks each newline as `LineBreaks.Marker` (``, one char for one char) and `RegisteredDocxTemplate.Render` splits every marked `w:t` once per part, alongside `Anchors.StripAll`. The marker is written *after* `XmlCharSanitizer.Strip`, which removes that character — that ordering is what guarantees a marker in the tree is one Parchment put there, and is why the pass can run over a whole part without tracking which text came from a substitution. A markdown template's non-body parts get the same pass in `RegisteredMarkdownTemplate.RenderNonBodyParts`. Its body gets no whole-part pass; `TokenValueHelpers` marks list items in either flow, so `MarkdownTokenBlocks.Insert` runs `LineBreaks.Apply` over the elements an `OpenXmlToken` produced, and only those. Editable-field values deliberately skip it: they round-trip through extraction, where a `w:br` has no text form.
   - **Table cells** (`Word/TableCells.cs`): Word refuses to open a document holding a `w:tc` that does not end with a `w:p`, and `OpenXmlValidator` does not report one, because the schema allows it. A removed branch, an empty loop, or a structural replacement that produced nothing leaves a cell empty; one that produced a table leaves the cell ending with it. The removal sites do not each check for that — `TableCells.EnsureFinalParagraph` runs once per part beside the two passes above and appends an empty paragraph where one is missing. A block-level `w:sdt` or `w:customXml` is not a block of its own: the pass reads through it, as Word does, so a cell whose content control ends with a table is still open, and one whose control ends with a paragraph is closed and left alone. The paragraph is appended to the cell, after the control, never to the control's content — for an editable field that content is the value extraction reads back. A cell whose only block is a control with no content is left alone as well, because Word opens it. `RegisterDocxTemplate` runs it over every part as well, so a cell the template itself left open is closed in the snapshot, including in a part no render reads. The markdown flow runs it over the body as well (a pipe-table cell whose `[Html]` value is a table) and over its non-body parts.
   - **Footnotes and endnotes** (`Word/NoteReferences.cs`): a note and its reference sit in different parts and are tied by id alone. Word refuses to open a document in which two references name one note, and `OpenXmlValidator` does not report it. A loop clones the reference with every iteration, and an empty loop or an unchosen branch removes it, so `NoteReferences.Apply` runs once over the body after every part has been rendered and cleaned up: each reference after the first to a note gets a copy of that note under the next free id in its part, and a note the template referred to that no reference names any more is removed. It has to stay after the per-part passes, because the copy is made from the *rendered* note — one taken earlier would duplicate the note's anchors, and `Anchors.BuildMap` binds one paragraph per anchor name. That is also why a copied note cannot see the loop variable: a notes part is validated and rendered on its own, against the model root. The ids the template's body refers to are read at registration (`NoteReferences.Read`), so a template with no note reference skips the pass, and a notes part is read only when a count actually moved. That read goes through `MainDocumentPart` instead of the token-part set — the one place a render reaches into a part that has no scope tree. Tests: `NoteReferenceTests`.
   - **Relationships of produced content** (`Word/PartRelationships.cs`): a relationship id resolves against the part holding the element that carries it, so a link or an image a token produces in a header, footer, footnote or endnote has to hang off that part. Left on the main part the id resolves nowhere, and Word reports the file as corrupt. One `PartRelationships` is made per part per render, in both flows, and shared by the runners of that part's loops and branches. What Parchment adds itself goes to its `Owner` directly: `OpenXmlContextImpl.AddImagePart`, and the markdown link renderers through `OpenXmlMarkdownRenderer.Part`. OpenXmlHtml and Excelsior take a `MainDocumentPart` and nothing else, and an `OpenXmlToken` or `MutateToken` delegate is handed nothing else either, so `ScopeTreeRunner` snapshots the main part's ids before a token produces, and `Claim` then moves to the owner whatever the main part gained that the produced elements refer to, pointing their `r:` attributes at the new id. The new id comes from `RelationshipIds`, so the random one Excelsior gives a link does not reach a non-body part. Three limits, each deliberate. Only what the main part *gained* is moved: an id it already held cannot be told apart from an id of the owner, since the two parts number independently, so a delegate that reuses a relationship the main part held before it ran still refers to the main part. A `MutateToken` is claimed for the elements it added, never for what its host already held, which is the template's and refers to the owner. And the main part's copy is dropped by `Complete` once the whole part is rendered, not at the move: OpenXmlHtml numbers an image and its `wp:docPr` one past the highest `rImage{n}` the main part holds, so dropping the first image of a header early would give its id to the second. A new producer of content that can land in a non-body part has to go through `RenderTokenValue`, or make the same snapshot and claim; a new relationship Parchment adds itself has to go to the owner, never to `mainPart`. Tests: `NonBodyPartRelationshipTests`.
   - **What a removed paragraph carried** (`Word/ParagraphContent.cs`): a block tag paragraph and the host of a solo structural token are recognised by their text alone, by the runner and by the validators, so neither removal can assume the paragraph is otherwise empty. Tag paragraphs go through `ScopeTreeRunner.RemoveTag` and solo hosts through `ApplyOne`; a new site that removes either has to do the same. When `ParagraphContent.HasBesidesText` finds something — a page break, a drawing, a note reference — only the text is removed: a tag paragraph stays where it was, and a solo host is split around its text by `ParagraphSplicer.Split`, each half kept only when it holds something. A tag paragraph is outside the block it delimits, so what it keeps is kept once, whichever branch is chosen. The scope tree follows document order, which lists the tokens of a text box anchored on an open tag at the head of the block's body, where the inner runner never finds them; `ProcessCarriedAsync` runs them in the enclosing scope. A `w:sectPr` is left on an empty stand-in paragraph, recorded in a list shared like the produced tables, and the root runner's `SettleSectionBreaks` moves it onto the preceding paragraph once every removal, iteration and replacement has run — the neighbour is not final before that. The stand-in stays after a table and after a paragraph that ends a section itself. What is deliberately not counted is listed on `ParagraphContent` (bookmarks, comment anchors, fields, `w:lastRenderedPageBreak`, tabs and line breaks): counting any of them leaves an empty paragraph in output that is clean today. Tests: `TagParagraphContentTests`.

**Important**: `ScopeTreeRunner` uses Fluid's actual AST nodes (`Fluid.Ast.Expression`, `ForStatement`, `IfStatement`, `OutputStatement`) at runtime. NO hand-rolled loop iteration via reflection, no string-render of conditions to `"true"`/`"false"`. `IdentifierVisitor` is only for **registration-time** validation against a .NET `Type`.

### Flow B — Markdown template (`RegisterMarkdownTemplate<T>` / `Render`)

Whole `.md` source is one Fluid template parsed once. `[ExcelsiorTable]` tokens are rewritten to markers (`MarkdownExcelsiorTables.Rewrite`) *before* that parse, so the cached template carries markers and a render never re-scans the source; `MarkdownExcelsiorTables.Apply` swaps each marker's paragraph for the built table after Markdig, before the TOC is written and before pagination — a table is taller than the marker it replaces, so every page number after it moves. `[Html]` / `[Markdown]` members are handled by a second registration-time rewrite (`MarkdownFormats.Rewrite`, run after the Excelsior pass so a marked line is already a marker): each plain-path token of an annotated member gets `| html` or `| markdown` appended, which is what exempts it from `MarkdownEncoder`. Both rewrites find their tokens through `Markdown/MarkdownOutputTokens.cs`, which locates each `{{ ... }}` in the text and classifies it by parsing that one token with Fluid, so every spelling Fluid reads as the same token is taken the same way: `{{- Member -}}`, `{{ Owner['Member'] }}`, a token broken over several lines. A rewritten token keeps its whitespace-control dashes (a dashed table token becomes `{{- 'marker' | raw -}}`), and "alone on its line" is measured from the token's first line to its last. The docx flow reaches the same place differently — `ScopeTreeRunner.TryResolveFormatted` reads `FormatMap` per token at render — but both resolve against the model root by dotted path, so an annotated member of a loop item is unresolved in either. At render:

1. Render cached `IFluidTemplate` against model → final markdown text, through `MarkdownEncoder` (`Liquid/MarkdownEncoder.cs`) rather than `NullEncoder`. The template is assembled as text and only then parsed, so an unescaped value is not data but more template — see `readme.md` → "Bound values are escaped" for the user-facing contract. Fluid applies the encoder at output only, so conditions and filter inputs still see the raw value. Opting out is `Fluid.Values.StringValue(text, encode: false)`, which is what `raw` does and what `Filters` and the `TokenValue` converter in `SharedFluid.BuildMarkdownOptions` return; a `TextToken` stays encoded, since it is a plain string and not a claim that the value is markup — the converter both option sets share has already made it a `StringValue` by then. Newlines become `<br />` (not a hard break, which needs a real newline in the source and would end a table row) and `HtmlInlineRenderer` renders that to the same `w:br` the docx flow reaches via `LineBreaks`. Two block constructs have no character a backslash can defuse, so each is closed elsewhere. Indentation: the first leading space or tab of a value is written as `&#32;` / `&#9;`, which CommonMark reads as the character but never as structural whitespace, and `HtmlEntityInlineRenderer` writes the reference back out as text (Markdig keeps a reference as its own inline, and an inline with no renderer is skipped without a trace). `[TOC]` / `[SECTION]`: these are plain text that `TableOfContents` and `SectionBreaks` recognise after parsing, and an escaped bracket is still the text of a bracket, so a value's leading `[` is written as `&#91;` instead. `IsMarker` asks for a paragraph of nothing but `LiteralInline`s, and the reference is an inline of another type, so a paragraph a value opens is never a marker while `\[TOC\]` typed in a template still is. A new text-shaped marker has to keep that "literals only" test, and has to open with a character `MarkdownEncoder.LeadingReference` covers. The one position-dependent rule is a link or image destination (`[text]({{ Url }})`, `![alt](images/{{ File }})`): a space or control character there ends the destination, and no backslash escape exists for it, so it is written as a numeric character reference (`&#32;`), which a destination resolves back to the character — the url or file path arrives as bound. Fluid passes the encoder the value alone (`StringValue` calls `Encode(string)`, never the `TextWriter` overloads), so each render constructs a `MarkdownEncoder` over its own `StringBuilder` and the encoder reads the position from the tail of what has been written (`InLinkDestination`); `MarkdownEncoder.Default` has no output and never applies the rule. Only an inline destination is recognized: a reference definition (`[label]: {{ Url }}`) is indistinguishable from prose, and an autolink ends at a space by design. The cached template has every `OutputStatement` wrapped (`MarkdownBlankOutputs.Instrument`, after validation, which reads the statements as written) so a render records where a value came out blank, and `MarkdownBlankOutputs.Strip` drops the emphasis delimiters around exactly those places before the text is parsed: markdown has no empty emphasis, so `**{{ A }}**` would otherwise print `****` or, alone on a line, become a thematic break. It records positions rather than writing a placeholder, measures what was written rather than re-evaluating the expression (a filter can park a value as a side effect), and tracks only the render's own writer, so a blank value inside `{% capture %}` is not covered.
2. `Markdig.Markdown.Parse(text, MarkdigPipeline.Pipeline)` → `MarkdownDocument`.
3. Clone the registration snapshot of the optional `styleSource` docx (or built-in blank), detach its `<w:sectPr>` (page size, margins, header/footer refs), walk markdown AST through `OpenXmlMarkdownRenderer`, append, re-attach sectPr. The snapshot is baked by `TemplateStore.BakeStyleSource`: its body is already emptied down to that one sectPr as a direct child, so a render never parses the sample document a Word-authored style source carries, and `compatibilityMode` is already stamped when the style source has a settings part of its own. A settings part that has to be *created* is still created by the render, after any numbering or image part, because creating it at registration would reorder the package and the relationships and change the output bytes. The snapshot is shared by concurrent renders and never mutated; each render works on its own clone, which matters for the sectPr because `SectionBreaks` rewrites it. `[SECTION]` markers make that sectPr the *first* of several rather than the only one: `SectionBreaks.TryWrite` emits a paragraph carrying only the orientation and margins the template declared, and `SectionBreaks.Apply` — run after the Excelsior and html swaps, before the sectPr is re-attached and before the TOC is written — rewrites each of those into a full section cloned from it. The preserved sectPr is mutated in place to whatever the last marker declared, because a `<w:sectPr>` describes the section that *ends* at its paragraph while the marker reads as "from here on". `Apply` never writes an empty section, which Word shows as a blank page ahead of the content: a marker whose previous sibling is the break before it (or that has none, at the top of the body) is removed and only replaces the settings in force, and a break left as the last child of the body is removed with its sectPr becoming the final one. Both are judged on the finished body, after the swaps, so a marker's position in the template source says nothing about either.
4. Header/footer parts, styles, theme, font tables passed through verbatim — renderer only mutates `Body` and (additively) `NumberingDefinitionsPart`.

`MarkdigPipeline` enables: emphasis-extras, grid + pipe tables, autolinks, list-extras (alpha + roman), smarty pants, **generic attributes** (`{.StyleName}` for attaching Word styles to headings/paragraphs — renderer honors first class on each block).

Autolinks are registered by hand rather than through `UseAutoLinks`, so that the parser is `BoundAutoLinkParser` (`Markdown/BoundAutoLinkParser.cs`). An autolink is the one construct that reads a bound value's backslash escapes verbatim *and* still has to work — its text is its target — so the escapes are undone there, after the link has been delimited: `BoundAutoLinkParser` for a bare url, `AutolinkInlineRenderer` for the `<…>` form. Markdig ends a bare url without regard to escapes, which can leave the backslash inside the link and the character it escaped outside; the parser hands that backslash back to the source, so the character stays escaped. A `file:` autolink is left as written, since a backslash is a path separator there.

### `OpenXmlMarkdownRenderer` — container stack pattern

`Markdown/OpenXmlMarkdownRenderer.cs` subclasses `Markdig.Renderers.RendererBase` (NOT `TextRendererBase` — no `TextWriter`). State is `Stack<ContainerState>` where each holds `{ List<OpenXmlElement> Blocks, List<OpenXmlElement> CurrentRuns }`. Inline renderers append runs to `Top.CurrentRuns`; block renderers call `FlushParagraph()` to wrap accumulated runs into `<w:p>`. A table cell pushes/pops a new container state; a list item or a block quote writes into the container around it, under an indent. **One renderer per render** — do not cache; the stack is mutable.

Word merges two `w:tbl` siblings into one table, so `AddBlock` writes an empty paragraph before a table that would directly follow another (`Word/AdjacentTables.cs`). Because list items and block quotes share the enclosing container, that one check covers the body, both of those, a grid-table cell, and a `[Markdown]` value in the docx flow, which is rendered here. It holds only while every table reaches its container through `AddBlock`. The two swaps that follow the walk in the markdown flow can bring tables together again, and each separates what it touches: `MarkdownExcelsiorTables.Replace` before the table it inserts (the emptied host already follows it), and `MarkdownTokenBlocks.Remove` while it re-attaches the children of each parent that lost a host. A new pass that removes or replaces a paragraph of rendered markdown has to do the same. Tests: `AdjacentTableTests`.

Every inline `MarkdigPipeline` can produce has a renderer registered in the constructor, and has to: `RendererBase` writes nothing for a leaf inline no renderer accepts — and only the children of a container — without raising anything, so a missing renderer is text silently absent from the document. That is how entities (`HtmlEntityInline`), angle quotes (`SmartyPantType` kinds with no glyph) and unmatched delimiters went missing. `DelimiterInlineRenderer` is registered for the base type because more than one parser leaves a delimiter in the tree: the link parser an unclosed `[`, and the pipe table parser any `|` nested in emphasis or following another delimiter in a paragraph that turned out not to be a table. `InlineCoverageTests.EveryInlineThePipelineCanProduceHasARenderer` reflects over Markdig's inline types — the core namespace plus the namespace of each enabled extension — so turning on another extension fails there until its inlines render, and `SmartyPantInlineRendererTests.EveryKindHasAGlyph` does the same per kind. `LinkInlineRenderer.ExtractAlt` keeps its own switch over the same inlines for image alt text, which neither test reaches.

`FlushParagraph` folds adjacent runs that have one `w:t` and equal `RunProperties` into one. Markdig splits a literal at every backslash escape, and `MarkdownEncoder` emits one for each punctuation character in a bound value, so without this ordinary prose triples its run count ("on-call" alone becoming two runs) for no visible difference. It has to happen at flush and **not** in `AddRun`: an inline renderer can still reach back and mutate what it already added — `EmphasisInlineRenderer` applies its formatting to every run written since it started, by index — so merging at add time both fuses a run into its neighbour before the formatting lands and shifts the indices under the renderer. By flush time every inline in the paragraph is final.

The one fold that does happen at add time is `AddLiteral`, which appends a literal to the run of the literal before it instead of building a `Run` and a `Text` for the flush to fold away again. It is safe only because of what it checks, and each check is load-bearing: the previous literal is the inline's `PreviousSibling` (adjacent siblings sit under the same emphasis, in the same link and between the same inline html tags, so nothing can format one and not the other, and no renderer's index range can start between them), that literal's run is still the last entry of the current container's `CurrentRuns`, and neither piece holds a tab. Runs written inside `LinkInlineRenderer.WriteHyperlink` are bracketed by `BeginUnfoldedRuns` / `EndUnfoldedRuns` and never folded, because they are moved into the `w:hyperlink`, which the flush does not look inside, so folding them there would change the output. A new renderer that takes runs out of `CurrentRuns` before the flush has to do the same. Tests: `LiteralFoldingTests`.

Whether two `w:rPr` are equal is decided by `Word/RunPropertiesComparer.cs`, which walks both trees instead of comparing `OuterXml` — that builds a writer and a string per side for every adjacent pair, and was most of what a render of emphasised bound values allocated. The answer has to stay the one the xml comparison gives, since any other answer merges different runs and changes the output: a missing `w:rPr` is not an empty one, attributes are compared in written order, `mc:` attributes and namespace declarations count, and an unknown element is still compared by its xml. `RunPropertiesComparerTests` asserts every case against `OuterXml` as well as against the expected answer.

`HtmlBlock` delegates to `OpenXmlHtml.WordHtmlConverter.ToElements(html, mainPart, settings)`, passing `HeadingLevelOffset` from current heading depth. **OpenXmlHtml ≥ 0.4.0 required** — heading-offset parameter was added for Parchment.

`HtmlInline` (`<em>`, `<strong>`, `<u>`, `<s>`, `<sub>`, `<sup>`, `<br>`) handled directly by `HtmlInlineRenderer`, NOT through OpenXmlHtml. Markdig delivers inline HTML as separate AST nodes (open tag, literal text, close tag), so renderer maintains a stack of active `RunProperties` mutators (`PushInlineHtmlFormat`/`PopInlineHtmlFormat`). `AddRun` applies the active stack to every emitted `Run`. The stack is cleared at the end of each leaf block's inline content (`RendererInlineExtensions.WriteLeafInline`), so an unclosed tag ends with its paragraph, heading, list item or table cell instead of formatting the rest of the document. `<br>` becomes a `Break` run. Unknown tags fall through as literal text.

`AddRun` only formats a `Run` it is handed directly. A renderer that adds its runs already wrapped — `AutolinkInlineRenderer` adds one finished `Hyperlink` — has to call `ApplyInlineHtmlFormats` on the runs inside first, or `<b><https://example.com></b>` loses the bold. `LinkInlineRenderer` does not need to: the runs of its text went through `AddRun` before it wrapped them.

**Character style precedence.** A run carries one `w:rStyle`, and four inlines can ask for one. Which wins goes by what asked, not by nesting order: emphasis (`**text**{.Lead}`), then a classed span, then inline code (`` `code`{.Mono} ``), then the link (`Hyperlink`, or the link's own `{.Name}`). No renderer compares ranks; the order falls out of when each one writes. Code sets its style as the run is built; `AddRun` then applies the open spans, replacing it; a link assigns only where nothing is set (`RunStyle ??=`); emphasis runs after its children are written and replaces whatever is there, including on runs inside a `Hyperlink`. Within one kind the nesting decides: the innermost span, the outermost styled emphasis. Direct properties (bold, underline and the rest) do not compete, so every enclosing inline contributes its own. `CharacterStylePrecedenceTests` renders every pair in both orders and asserts identical `w:rPr`.

Markdown `![alt](url)` images delegate to OpenXmlHtml — `LinkInlineRenderer.WriteImage` synthesizes a one-shot `<img src="<url>" />` and hands to `WordHtmlConverter.ToElements`. So data URIs, `file://`, absolute/CWD-relative paths, and `http(s)://` all flow through `OpenXmlHtml.ImageResolver` regardless of source. **Do not** reintroduce a parallel "resolve to data URI in Parchment first" path inside `LinkInlineRenderer` — duplicates ImageResolver and bypasses `ImagePolicy`.

### Image policies (`Word/ImagePolicies.cs`)

`TemplateStore` exposes `init`-only `LocalImages` and `WebImages` (`OpenXmlHtml.ImagePolicy`), both defaulting to `ImagePolicy.AllowAll()`. The store builds an internal `ImagePolicies` record (`(LocalImages, WebImages)` + `BuildSettings(headingOffset, numberingSession)`) and threads it through every `OpenXmlHtml.WordHtmlConverter.ToElements` call site:

- `RegisteredDocxTemplate` → `ScopeTreeRunner` (and cloned runners in loops/if branches) — for `HtmlToken` AND when `ScopeTreeRunner` calls `MarkdownRendering.Render` for `MarkdownToken`.
- `RegisteredMarkdownTemplate` → `MarkdownRendering.Render` → `OpenXmlMarkdownRenderer` (exposed as `ImagePolicies` property), read by `HtmlBlockRenderer` and `LinkInlineRenderer`.

`AllowAll` is the deliberate default because Parchment renders developer-bound content; OpenXmlHtml defaults to `Deny()` because *it* doesn't know its HTML's source. Don't chase OpenXmlHtml's default — Parchment's threat model is different.

**Lockstep**: any new `WordHtmlConverter.ToElements` call MUST consume `ImagePolicies` (via `imagePolicies.BuildSettings(...)` for runtime, or `renderer.ImagePolicies.BuildSettings(...)` from inside a markdown renderer). A bare `new HtmlConvertSettings()` falls back to OpenXmlHtml's `Deny()` and reintroduces the alt-text-fallback bug for `<img>`. A call that can convert a list also has to go through `WordNumberingState.ConvertHtml` rather than reach the converter directly — see the numbering entry under "Non-obvious gotchas".

### Fluid integration (`Liquid/SharedFluid.cs`)

Single static `FluidParser` and `TemplateOptions` shared across all renders (Fluid documents these as thread-safe; recommends per-process singletons). `RegisterModel(Type)` walks model's reachable type graph and calls `MemberAccessStrategy.Register<T>()` on every POCO via reflection. **Load-bearing**: Fluid 2.x's `DefaultMemberAccessStrategy` does NOT auto-discover nested types from a model passed via `TemplateContext(model)` — without the recursive walk, `{{ Customer.Name }}` returns empty.

Filters (`Liquid/Filters.cs`): `markdown`, `html`, `escape_xml`, `bullet_list`, `numbered_list`. Filters returning a `TokenValue` (wrapped in `ObjectValue`) trigger structural replacement at the substitution site. In the markdown flow all of them return `encode: false` — each is a statement that the result is syntax — so a new filter that assembles markdown has to opt out the same way *and* escape the model-supplied parts itself, the way `BuildList` escapes items while keeping its markers. A filter that merely transforms a value (`upcase`) must not opt out: its output is still data. Opting out also drops the encoder's newline → `<br />` rule, so `escape_xml` repeats it (`MarkdownEncoder.Break`) — a newline left in the source is whitespace to the markup, and a blank line ends the html block the value was escaped for. Markdown flow only: the docx flow lands the value in a run, where `LineBreaks` already handles the newline and a tag would print.

**A filter that produces a token has to be the last of its chain** (`Liquid/TokenFilterOrder.cs`, `PARCH037`). The filter after it is handed the token instead of text: a `TokenValue` in the docx flow, which Fluid stringifies to its type name, and the parked-html marker in the markdown flow. The file is linked into the source generator's csproj, so the four validators read one definition of which filters those are; a new filter in `Filters` that returns a `TokenValue` has to be added there. The set differs by flow — see "Known and deliberate asymmetries" below.

A value prints as the same text in both flows. The docx flow takes `ToStringValue()` of each token (`ScopeTreeRunner.InterpretFluidValue`); the markdown flow has Fluid write the value, and `NumberValue.WriteToAsync` reformats a number (`1234.50` → `1234.5`, `10.00` → `10.0`). `MarkdownNumberText` therefore wraps every output expression of a markdown template after validation, turning a number into its `ToStringValue()` text at the point it is written, so it is still a number for comparisons and math filters. `TimeSpan` and `TimeOnly` are fixed for both flows by the value converter in `SharedFluid.BuildOptions` (`c` and `HH:mm:ss`, invariant), since Fluid's defaults are a 1970 date in the machine's time zone and a time without seconds.

`html` is the exception to "unencoded is enough". Markdown source written into a markdown template is already what it will be parsed as, but html written there is only html if Markdig independently classifies it as such — `<span>a *b* c</span>` emits the span as literal text and turns `*b*` italic, which is markdown's answer rather than html's. So in that flow the source is parked and a marker emitted (`Formats/MarkdownHtmlBlocks.cs`), and `RegisteredMarkdownTemplate.Render` swaps the marker's paragraph for `WordHtmlConverter` output right after `MarkdownExcelsiorTables.Apply` — before the TOC and pagination, since converted html is taller than the marker it replaces. Parked at render rather than rewritten at registration because the value only exists at render; `MarkdownFormats` can rewrite the *token* early but not resolve it.

**Both routes park through the same store, and it is an `AsyncLocal`.** An `HtmlToken` reaches the markdown flow through the value converter in `SharedFluid.BuildMarkdownOptions`, whose Fluid signature is `Func<object, object>` — no `TemplateContext`, and `FluidValue.WriteTo` is handed only an encoder and a culture. The filter *does* get a context and could have used `AmbientValues`, but two mechanisms is what left `HtmlToken` passing through while `| html` converted, so both go through `MarkdownHtmlBlocks.BeginScope`. The scope wraps the liquid render alone: `Render` lifts the map off it the moment Fluid finishes and passes it to `Apply` explicitly, so the ambient window is only where it is unavoidable. AsyncLocal rather than ThreadStatic because a render is async — the flow is what owns it, which `ConcurrentRendersDoNotShareParkedHtml` pins.

Markers on both paths are wrapped in `U+E000`. That is not decoration: `Apply` finds a marker's host with `Contains`, so an unterminated `…-1` would be found inside `…-10` and the first marker reported as sharing its block with what is really the eleventh's. It also means no rendered value can collide with a marker. Because converted html replaces the block it lands in, a marker that is not alone in its paragraph is a render error rather than a silent discard — the same answer `[ExcelsiorTable]` gives.

### Source generator (`src/Parchment.SourceGenerator/`)

User-facing overview, attribute placement, and PARCH001–PARCH012 are in `readme.md` → "Source generator (recommended)". The notes below cover implementation details needed for navigating the SG code.

`netstandard2.0;net10.0`, packaged inside `Parchment.nupkg` under `analyzers/dotnet/roslyn5.0/cs` and `analyzers/dotnet/roslyn5.3/cs`. `IIncrementalGenerator` + `ForAttributeWithMetadataName("Parchment.ParchmentModelAttribute")`. The attribute is parameterless — the template is found by **convention**: the AdditionalFile named after the type plus the `.parchment` marker (`Invoice.parchment.docx` or `Invoice.parchment.md`; both/none → PARCH020/PARCH004, matching in `TemplateConvention.MatchByTypeName`). The marker is what lets `build/Parchment.props` glob templates into `ParchmentTemplate`, and `build/Parchment.targets` copy them into `AdditionalFiles`, without a csproj entry — an unmarked file is filtered out at the `AdditionalTextsProvider` stage, so a readme is never read, let alone parsed as liquid. The glob is in the props file because props are imported ahead of the project body: declared in the targets it would run after the body, and a `<ParchmentTemplate Remove="..." />` there would act on an empty list. The targets file does what has to wait for the body — the copy into `AdditionalFiles`, less the discovered copy of any file the project also declares. Same attribute supports **both** docx and markdown — SG branches on the matched file's extension. Pipeline collects `targets`, `docs`, `markdowns`, `dotxes` in four parallel `AdditionalTextsProvider` stages (each cached separately for incrementality), `Combine`s them, dispatches per target.

**Emission is a module initializer, not a helper.** The generated partial carries the template itself — docx/dotx bytes as base64 in an `[EmbeddedBytes("...")]` attribute on the nested `ParchmentGenerated_{Model}` class, markdown as a string literal — and a `[ModuleInitializer]` that hands it to `GeneratedRegistration.RegisterDocxTemplate` / `RegisterMarkdownTemplate` (which store a definition in `GeneratedTemplateDefinitions`) plus the accessor registrations. The bytes are an attribute argument, not a string the code loads, because of where the compiler puts each: a loaded string goes to the metadata user-string heap as UTF-16, which every literal of the assembly shares and which stops at 2^24 bytes — the templates of a project could total about 6.2 MB before the consumer's build failed with a locationless `CS8103` — while an attribute argument goes to the blob heap as UTF-8 (4/3 of the template in the assembly, not 8/3; identical values stored once; no shared ceiling). The initializer passes only `typeof(ParchmentGenerated_{Model})`; the attribute is read and decoded when a store materializes the definition, so a model that is never rendered decodes nothing. Alternatives measured and rejected for what they cost every consumer compile: a `"..."u8` literal and a `byte[]` / `ulong[]` initializer both become one bound node per element (a 10 MB template: 2.2 GB, 4.9 GB and 1.0 GB of compiler memory, against 0.4 GB for a string). `EmbeddedTemplateTests` compiles generated output against the real runtime assembly (`CompiledGenerator`), since the limit only shows at emit. A `TemplateStore` materializes the definition on the model's first render (`TemplateStore.Resolve`, walking the model type's base chain). There is no `RegisterWith`, no `TemplatePath`, no CopyToOutputDirectory, and no manifest-resource staging — templates never exist beside the assembly.

**Docx flow** (mirrors runtime Flow A):

1. Matches AdditionalFiles by type name.
2. Reads docx via `AdditionalText.Path` (binary AdditionalFiles pattern — `GetText()` returns null for binary, and `File.ReadAllBytes` is banned by RS1035); raw bytes come off a `FileStream` under a local RS1035 pragma and travel through the pipeline as base64 (`DocxData.ContentBase64`) so a byte-only change (style tweak) still re-emits the embedded copy. The file is read **once**, with `FileShare.ReadWrite | FileShare.Delete`: `DocxArchiveReader` walks a `ZipArchive` over those same bytes rather than reopening the path, so a template open in Word still builds (`ZipFile.OpenRead` asks for `FileShare.Read` and is refused while Word holds write access) and the validated template is the embedded one. A `.dotx` goes through the same `ReadBytes`.
3. Finds the parts through the package relationships, not by file name: `_rels/.rels` names the main part (`word/document2.xml` is as legal as `word/document.xml`), and that part's own relationships name the headers, footers, footnotes and endnotes — the set `DocxCloner.EnumerateParts` scans, in the same order. Each is walked via `XDocument`, in the transitional namespace or the Strict Open XML one (the runtime's SDK reads both, so both are validated). A zip with no main part, or whose main part is not a Word document, is `PARCH006`. Also probes the settings part for `<w:removePersonalInformation/>` — absence emits `PARCH012` (warning). The runtime clones the template's `settings.xml` into the output, so the warning surfaces a PII-leak path at compile time.
4. Tokenizes paragraph `InnerText` into `{{ ... }}` / `{% ... %}` sites, hands each to `Fluid.FluidParser` and walks the AST with `IdentifierVisitor : Fluid.Ast.AstVisitor` to collect member-access paths. Fluid.Core + transitive closure (Parlot, Microsoft.Extensions.FileProviders.Abstractions, Microsoft.Extensions.Primitives, TimeZoneConverter, plus System.Text.Json + Microsoft.Bcl.HashCode on netstandard2.0) merged into `Parchment.SourceGenerator.dll` at build via `PackageShader.MsBuild` (`Shade="true"`), so analyzer ships as a single self-contained DLL. The closure has to be shaded *in full*, including leaves that no first-party code references directly: an unshaded leaf keeps being bound by its original identity, so analyzer hosts that do not happen to supply it fail to load the generator. MSBuild supplies `Microsoft.Extensions.Primitives`, ReSharper/Rider InspectCode does not, so a gap there stays invisible to `dotnet build` and surfaces only as bogus PARCH004 under InspectCode. SG keeps a parallel `TokenScanner.cs` rather than sharing source — runtime types are internal and depend on `DocumentFormat.OpenXml`, which doesn't work in a netstandard2.0 analyzer.
5. Validates against model's `ITypeSymbol` (Roslyn semantic model, not reflection).
6. Emits diagnostics `PARCH001`–`PARCH008`, `PARCH010`–`PARCH012`, `PARCH028`, `PARCH035`, `PARCH037`. `PARCH035` (unbalanced block tags) comes from `BlockStructure`, a mirror of the nesting walk in the runtime `ScopeTreeBuilder` that returns the builder's own message; the builder cannot be linked in because it builds nodes over OpenXml paragraphs. It runs once per part (`DocxData.ParagraphParts` → `Token.Part`), as the runtime builds one scope tree per part. `Parchment.Tests/Docx/StructuralLockstepCases.cs` is compiled into both test projects and lists every structurally wrong template with the runtime message and the diagnostic id: **a new throw in `ScopeTreeBuilder` or the runtime `TokenScanner` needs a case there**, which fails the generator half until it reports the same thing. `PARCH028` needs to know which paragraphs share a parent, and an `XElement` cannot travel through the pipeline, so `DocxArchiveReader` numbers the parents and `DocxData.ParagraphContainers` carries one int per paragraph, parallel to `Paragraphs`; `TokenScanner` copies it onto `Token.Container` and `ValidateBlockContainers` compares the tags of each block. Generates the module initializer calling `GeneratedRegistration.RegisterDocxTemplate(typeof(TModel), typeof(ParchmentGenerated_{Model}), protection)` (protection argument only when non-default). Nested-class targets are wrapped in matching `partial {kind} {name}` declarations for every link in the enclosing-type chain — `BuildPartialSource` walks `target.EnclosingTypes` (outermost first). PARCH011 fires when any enclosing type isn't `partial`, and the initializer is *not* emitted in that case (otherwise CS0260 with no link back to the SG).
7. **Emits pre-compiled accessors** via `AccessorEmission.Emit(target.Shape, rootFqn)` — see "Design decisions → Source generator emits pre-compiled accessors" below for the four-dataset pipeline.

**Markdown flow** (mirrors runtime Flow B):

1. Matches AdditionalFiles by type name.
2. Reads via `AdditionalText.GetText(cancel)` into an equatable `MarkdownData` record. `File.ReadAllText` is **not** used — RS1035 bans it; canonical Roslyn path lets the SDK reuse cached `SourceText`. Test harness's `PathAdditionalText.GetText` returns real `SourceText` for `.md` (and `null` for `.docx`).
3. Hands the **whole file** to `FluidParser.TryParse` (one call, not per-token) — markdown templates have no paragraph boundaries. Parse failure → `PARCH006` with Fluid error.
4. `MarkdownValidator.Validate` walks the AST with loop-scope tracking: descends into `ForStatement` (binding `Identifier` → element FQN via `ShapeResolver.TryGetElementType`), `IfStatement` (incl. `ElseIfs`/`Else`), `OutputStatement`, `for-else`, `UnlessStatement`, `CaseStatement` (every `WhenStatement` option and body, and `Else`), `CycleStatement` (group and values), `TableRowStatement` (bound like a `for`), `CaptureStatement`, `LiquidStatement` and `IfChangedStatement`. The walk is a `switch` over statement types, not an `AstVisitor`, so a statement kind it does not name is skipped without a word: a tag Fluid gains has to be added here, where the runtime's `MarkdownReferenceValidator` inherits a default walk from `AstVisitor`. Each `MemberExpression` is collected via private `ExpressionPathCollector : AstVisitor` and resolved against `target.Shape` honouring scope. When loop source doesn't resolve to enumerable, loop var is bound to root type for body walk — cascade-noise suppression.
5. Emits `PARCH001`, `PARCH002`, `PARCH024` and `PARCH037`. `PARCH005` deliberately not emitted — Fluid parses whole markdown as one template; `Hello {% if x %}World{% endif %}` is legal at runtime. `PARCH007`/`PARCH008` (Excelsior) and `PARCH010` (`[Html]`/`[Markdown]` with filters) are docx-only. `PARCH024` is not: a format marker reached through a loop variable is unresolvable in both flows, because both match a token's path against a map keyed from the model root.
6. Resolves the **style document**: the `.dotx` named after the type (more than one → `PARCH021`), else the nearest `parchment.dotx` walking up the directory tree from the template (`TemplateConvention.FindSharedStyleDoc` — longest ancestor directory wins), else none. Generates the module initializer calling `GeneratedRegistration.RegisterMarkdownTemplate(typeof(TModel), "markdown literal"[, typeof(ParchmentGenerated_{Model})])` (the type carrying the style document's `[EmbeddedBytes]`). Same `AccessorEmission` pass as docx — symmetric emission keeps SG output predictable regardless of template shape. Dotx resolution is markdown-only: a docx template carries its own styles.

**Lockstep with runtime markdown flow**: runtime's `RegisterMarkdownTemplate` validates references via heuristic that skips loop variables by string-matching against source text. SG validates the *same* references via proper AST walk with explicit scope — strictly more accurate. SG sometimes catches loop-shadowing bugs the runtime misses — when tightening runtime's loop-variable detection, also revisit `MarkdownValidator`.

**Snapshot stability**: OPC packages are not byte-reproducible (zip timestamps, relationship ids), so the test docxes rebuilt per run would churn every base64 literal in the SG snapshots. `Parchment.SourceGenerator.Tests/ModuleInitializer` scrubs `EmbeddedBytes("...")` literals; what the bytes were is asserted within a single run by `TemplateConventionTests`.

`Parchment.SourceGenerator.csproj` has `<InternalsVisibleTo Include="Parchment.SourceGenerator.Tests"/>` — but signed assemblies don't honor IVT without public-key match, so test-facing types (`TokenScanner`, `TokenKind`, `Token`) are `public`. Records use `init`, requiring the `IsExternalInit` polyfill in `Polyfills.cs` for netstandard2.0.

### Excelsior table dispatch (`[ExcelsiorTable]`)

A hook letting `{{ Property }}` resolve to a fully-formatted Word table rendered by [Excelsior](https://github.com/Papyrine/Excelsior) instead of default string substitution. Parchment takes a hard `PackageReference` on `Excelsior` (version pinned in `src/Directory.Packages.props`); the attribute lives in Parchment (`Parchment.ExcelsiorTableAttribute`), so dep direction is Parchment → Excelsior.

**Runtime path** (`src/Parchment/Excelsior/`):

1. `TemplateStore.RegisterDocxTemplate<TModel>` calls `ExcelsiorTableMap.Build(typeof(TModel), name)` BEFORE scanning parts. Recursively walks `TModel`'s property graph, collecting every `[ExcelsiorTable]`-marked collection under its dotted path (e.g. `"Customer.Lines"`). Each entry stores `(DottedPath, ElementType, Func<object, object?> Getter)` — getter is a chained closure with null-short-circuiting at every step.
2. `ExcelsiorTokenValidator.Validate` runs immediately after `ReferenceValidator.ValidateTree`. For each substitution token whose first identifier matches a map entry: (a) token must sit alone in its host paragraph, (b) parsed `OutputStatement.Expression` must be exactly a `MemberExpression` (no filters/arithmetic/literals). Both throw `ParchmentRegistrationException`.
3. `RegisteredDocxTemplate` stores the map and passes both it AND original `object model` to every `ScopeTreeRunner` (including cloned runners in loops/conditionals).
4. `ScopeTreeRunner.EvaluateTokenAsync` consults `TryResolveExcelsiorTable` FIRST. If matched, calls `entry.Getter(rootModel)`, synthesizes `TokenValue.OpenXml(ctx => [ExcelsiorTableBridge.BuildTable(elementType, data, mainPart)])`. Existing `TokenValue.OpenXml` structural-replacement path handles the rest — which is why the token must sit alone.
5. `ExcelsiorTableBridge` uses `ConcurrentDictionary<Type, BuilderInvoker>` to cache reflection-built delegates per element type. Each invoker closes the generic `BuildTable<TElement>` overload over the element type (`MethodInfo.MakeGenericMethod`) and calls it through `MethodInfo.Invoke`; that overload is plain code — `new WordTableBuilder<TElement>(data)`, the attribute's styles, the `Configure` callback, then `Build(mainPart)`. Reflection cost amortized per element type.

**SG path** (`src/Parchment.SourceGenerator/`):

1. `ShapeBuilder.HasExcelsiorTableAttribute` matches by FQN string (`"global::Parchment.ExcelsiorTableAttribute"`) — SG can't `typeof()` it (doesn't reference Parchment.dll).
2. `MemberEntry` has `IsExcelsiorTable` bool flag — primitive for incremental pipeline cacheability.
3. `TokenScanner.ParseSubstitution` sets `Token.IsPlainIdentifier` via `IsPlainMemberAccess` (single `OutputStatement` wrapping a bare `MemberExpression`).
4. `ShapeResolver.IsExcelsiorTableMember` walks segment path (honoring loop scope), returns true if final member carries the flag.
5. `ParchmentTemplateGenerator.ValidateExcelsiorToken` (in Substitution case of `ValidateTokens`) gates on `IsExcelsiorTableMember`, emits `PARCH007` when `HasOtherContent` and `PARCH008` when `!IsPlainIdentifier`.

**Member shape (`PARCH034`).** `ShapeBuilder.IsTabular` sets `MemberEntry.ExcelsiorNotTabular` when the attributed member is not a sequence of a type with at least one public instance property or field (what Excelsior's column discovery reads). `ValidateExcelsiorShape` reports it from all three paths (docx, markdown, bindable) and `AccessorEmission.WalkForMaps` skips the entry. There is no runtime counterpart: with no reflection walk, an entry the generator does not emit does not exist.

Runtime and SG enforce same two rules via different mechanisms: runtime inspects Fluid AST directly; SG reads a boolean baked in by `TokenScanner`. Tests: `ExcelsiorTableTests` (runtime) and `ExcelsiorToken_*` (SG).

**`Configure` hook.** The attribute's `Configure` names a static method on the declaring type that receives the `WordTableBuilder<TElement>` after the attribute settings — the escape hatch for what an attribute cannot carry (per-column config, merged rows). The SG resolves it at compile time: `ShapeBuilder` turns the name into a qualified call target (or sets `ExcelsiorConfigureMissing` → `PARCH026`, with emission suppressed so the diagnostic is the only error), and `AccessorEmission` emits `b => Declaring.Method((WordTableBuilder<Element>)b)` into the map entry as an `Action<object>`. No name is resolved at render time — a wrong signature is an ordinary compile error in the generated call. The call is emitted into the root model's nested generated class, which sees a private method on the model and nowhere else, while the attributed member can sit on any reachable type or a base. So `ShapeBuilder.ResolveConfigure` asks `Compilation.IsSymbolAccessibleWithin(method, root)`: accessible is a direct call; otherwise, when the declaring type and everything enclosing it is `partial`, the member carries `ConfigureForwarder` entries and the call targets `ParchmentConfigure_{Root}_{Method}`, an `internal static` forwarder emitted into a partial part of the declaring type in a second file (`{hint}_Configure.g.cs`, because the model's file has a file-scoped namespace); otherwise `ExcelsiorConfigureInaccessibleOn` is set and reported as `PARCH026` (second descriptor, same id) with emission suppressed. The forwarder name carries the root so two models reaching one type do not declare the same member. `ExcelsiorTableBridge` invokes it after the attribute styles, so what Configure sets wins. The `GeneratorDriver` stub of the attribute must mirror new attribute properties, or test compilations silently drop the named argument.

### Html / Markdown property dispatch (`[Html]` / `[Markdown]`)

Parallel to Excelsior but for string properties: a `string`/`string?` property marked with user-defined `HtmlAttribute`/`MarkdownAttribute` (detected by type name — Parchment doesn't ship the attributes) or `[StringSyntax("html")]`/`[StringSyntax("markdown")]` causes its `{{ Property }}` to be structurally replaced. Html runs through `OpenXmlHtml.WordHtmlConverter.ToElements`; markdown runs through the same `MarkdownRendering.Render` used by markdown-template flow.

**Runtime path** (`src/Parchment/Formats/`):

1. `FormatMap.Build(modelType)` returns the SG-precompiled entries (or `Empty` — no reflection walk). Detection lives in `ShapeBuilder.DetectFormat`: `[HtmlAttribute]`/`[MarkdownAttribute]` by attribute class name, `[StringSyntax]` by FQN with `Syntax == "html" | "markdown"`. Conflicting markers (`[Html]+[Markdown]`, or either contradicted by `[StringSyntax]`) are `PARCH023` at compile time and excluded from emission. So is a marker on a member that is neither a `string` nor a `TokenValue` (`PARCH029`, reported from `ValidateFormatMarkerTypes` for docx, markdown and bindable targets); `TryResolveFormatted` falls through to plain evaluation if a non-string value arrives regardless.
2. `FormatTokenValidator.Validate` runs in `RegisterDocxTemplate` right after `ExcelsiorTokenValidator`. Only registration-time rule: parsed `OutputStatement.Expression` must be a `MemberExpression`. Solo-in-paragraph is **not** required — see splice below.
3. `ScopeTreeRunner.EvaluateTokenAsync` consults `TryResolveFormatted` AFTER `TryResolveExcelsiorTable`, before standard Fluid eval. Walks dotted path on `rootModel` via `PropertyInfo.GetValue`, returns `TokenValue.Html(text)`/`TokenValue.Markdown(text)`. Null strings → empty.
4. `TokenValue.HtmlToken` handled alongside `MarkdownToken`/`OpenXmlToken` in `BuildStructuralReplacements`; source string passed to `OpenXmlHtml.WordHtmlConverter.ToElements(..., mainPart, new())`. For non-solo tokens, `ProcessSubstitutionAsync` consults `ParagraphSplicer`.
5. `ScopeTreeRunner` takes `FormatMap` as ctor dep, propagates to cloned runners.

**Inline-aware structural replacement** (`src/Parchment/Word/ParagraphSplicer.cs`):

When `[Html]`/`[Markdown]` token shares its host paragraph with other text/tokens, `ScopeTreeRunner.ApplyNonSoloStructural` chooses:

- **Inline splice** — produced list is exactly one Paragraph (typical for inline-only HTML like `<b>x</b>`, or single-line markdown). `ParagraphSplicer.SpliceInline` rebuilds host's children as `[before token] + [produced paragraph's children, minus pPr] + [after token]`. Host's `pPr` preserved; produced `pPr` dropped.
- **Split** — produced list has multiple block-level elements or a non-paragraph (a table). `ParagraphSplicer.Split` trims the host in place to runs/text before the offset, builds an `after` paragraph from a host clone (preserving `pPr`) trimmed to runs/text after `offset+length`, and returns `[...produced, after]` to insert after the host (`StructuralReplacement.KeepHost`). The host has to stay the before half: tokens run in reverse offset order, so the ones before the split token are substituted after the split and would be lost on a clone. `DivideProperties` then takes the `pPr` children that mark one end of the paragraph off one of the halves: `w:sectPr` stays on `after` only (which is emitted even when empty, so the break also has a paragraph to sit on when the produced content ends with a table), `w:pageBreakBefore` and the list number stay on the host only. `after` keeps its `w:numPr` with `w:numId` 0 instead of losing it, so a numbered paragraph style cannot number it again. Everything else is formatting and stays on both, and nothing inherited from the style is resolved.

Both modes build halves from clones, so a text box anchored in a carried-over run is a copy and the paragraphs inside it are no longer the ones in the anchor map — and their nodes run after the host's. `ScopeTreeRunner.RepointNestedAnchors` re-indexes the nested paragraphs of the spliced result after either mode; anything new that clones part of a host has to do the same. Tests: `TextBoxTokenTests.TokensInATextBoxAnchoredInASplicedParagraphAreSubstitutedOnce`.

Two non-solo block-shaped tokens in the same paragraph throw `ParchmentRenderException` — splits would overlap, no defined composition. Author needs to give one its own paragraph.

**SG path** (`src/Parchment.SourceGenerator/`):

1. `MemberEntry` has primitive `IsHtml`/`IsMarkdown` bools.
2. `ShapeBuilder.DetectFormat(ISymbol)` matches attribute class name strings (`"HtmlAttribute"`, `"MarkdownAttribute"`) and `StringSyntaxAttribute` FQN `"global::System.Diagnostics.CodeAnalysis.StringSyntaxAttribute"`.
3. `ShapeResolver.TryResolveMember` yields the final `MemberEntry` for a segment path (honoring loop scope), so caller can consult both flags without walking shape twice.
4. `ParchmentTemplateGenerator.ValidateFormatToken` gates on `member.IsHtml || member.IsMarkdown`, emits `PARCH010` on `!IsPlainIdentifier`. **PARCH009 (legacy "must sit alone") is retired** — runtime now splices/splits.

**Lockstep**: both still enforce plain-member-access (`PARCH010` / runtime `RequirePlainIdentifier`). Tests: `FormatAttributeTests` (runtime, including `NonSoloHtml_*`/`NonSoloMarkdown_*`) and `FormatToken_*` (SG).

Loop-scoped tokens fall through — `FormatMap` is keyed on dotted paths from root model only (same as `ExcelsiorTableMap`). `{% for line in Lines %}{{ line.Body }}{% endfor %}` where `Line.Body` is `[Html]` won't trigger structural replacement — use `{{ line.Body | markdown }}` explicitly inside loops.

### String-list dispatch (auto bullet for `IEnumerable<string>`)

A substitution token whose dotted path resolves to `IEnumerable<string>` (incl. `string[]`, `List<string>`, `IReadOnlyList<string>`, etc.) auto-renders as a Word bullet list — same output as `{{ Tags | bullet_list }}`. **No attribute required**; detection is type-driven. No SG counterpart, no diagnostics — opportunistic, not validated.

**Runtime path** (`src/Parchment/StringLists/`):

1. `StringListMap.Build(modelType, name)` walks property graph. For each property: skip if `[ExcelsiorTable]` (Excelsior keeps ownership; attribute permits `string` element types and would otherwise be shadowed). Else if assignable to `IEnumerable<string>` (excluding `string` itself, which is `IEnumerable<char>`), add `(DottedPath, Func<object, object?> Getter)`. Same `ChainGetter`/`ShouldDescend`/per-branch `visited` discipline as `ExcelsiorTableMap`.
2. `ScopeTreeRunner.EvaluateTokenAsync` consults `TryResolveStringList` AFTER `TryResolveExcelsiorTable` and `TryResolveFormatted`. Dispatch order: Excelsior → Format → StringList → Fluid.
3. `TryResolveStringList` **gates opportunistically** instead of throwing on misuse:
   - Returns `null` if token isn't solo in its paragraph.
   - Returns `null` if parsed `OutputStatement.Expression` isn't a plain `MemberExpression` (user attached a filter — explicitly opting into Fluid).
   - In both cases, Fluid takes over — preserves backward compat.
4. When gates pass: calls `entry.Getter(rootModel)`, materializes with `.ToList()` (so deferred render delegate doesn't re-enumerate), returns `TokenValueHelpers.BulletList(items)` — same primitive the `bullet_list` filter uses (`TokenValue.OpenXmlToken` wrapping `IOpenXmlContext.CreateBulletNumbering()` + `ListParagraph` paragraphs).
5. `ScopeTreeRunner` takes `StringListMap` as ctor dep, propagates to cloned runners.

**Why opportunistic, not strict**: the existing `bullet_list` filter produces the same output, and pre-feature users wrote `{{ Tags | bullet_list }}` against `IEnumerable<string>` properties — strict validation would have broken `TokenOverrideTests.BulletListFilter`. Fall-through keeps the feature purely additive.

Loop-scoped tokens fall through — same root-only key limitation as `ExcelsiorTableMap`/`FormatMap`. Inside `{% for c in Customers %}{{ c.Tags }}{% endfor %}` use the explicit `bullet_list` filter.

Tests: `StringListTests` (Parchment.Tests/Docx). Scenario: `src/Parchment.Tests/Scenarios/string-list/`.

### Editable field dispatch (`[EditableField]`) + extraction

Two-way binding: marked members render as tagged content controls inside editable-range exceptions, the document is locked read-only, and `ParchmentExtractor` reads user edits back. User-facing docs in `readme.md` → "Editable fields (two-way binding)"; PARCH013–PARCH018 in the diagnostics list.

**Runtime render path** (`src/Parchment/Editable/`):

1. `EditableMap.Build(modelType)` returns the SG-precompiled entries (or `Empty` — no reflection walk). Entries carry getter, **parent-routed setter** (assigns on the object at the end of the parent path — never the root), `CanReach` (parent chain non-null), kind, `IsNullable`, `MultiLine`, `DateFormat`, all emitted by `AccessorEmission`. Model-shape errors are compile-time diagnostics: unsupported type / `bool?` (`PARCH013`), no public non-init setter (`PARCH014`), conflicting `[ExcelsiorTable]` or `[Markdown]`/`[StringSyntax("markdown")]` (`PARCH015`), invalid collection element, or a collection declared as a type the rebuilt `List<T>` / `T[]` cannot be assigned to (`PARCH022`; `ShapeBuilder.AcceptsRebuiltList`, lockstep with `ParchmentExtractor.ReconstructCollection`), a struct on the path to the member (`PARCH032`). `[Html]`/`[StringSyntax("html")]` is **not** a conflict — it selects the `Html` kind (editable rich text, see the Html sub-point under 4).
2. `EditableTokenValidator` runs after `FormatTokenValidator` in `RegisterDocxTemplate`. It applies its rules exactly where the runner holds an editable map — the root map outside every loop, an editable collection's item map (`ScopedToItem`, so a token through the loop variable) directly inside a top-level loop over it — and skips every other occurrence (non-body part, any other loop body), which renders read-only through Fluid. Rules: plain member access only; duplicate path rejected (body part only — the dotted path is the control tag; a paragraph inside an `mc:Fallback` is not counted, see the text box note under Extraction); editable token sharing a paragraph with an Excelsior/Format token rejected (structural splice/split clones paragraph halves and would corrupt the perm-range markers). A render-time guard in `ScopeTreeRunner` catches the same conflict for `TokenValue`-typed properties that only turn out structural at render.
3. `SettingsProtection.Apply` writes `w:documentProtection w:edit="readOnly" w:enforcement="1"` into the settings part at **registration** (canonical bytes), gated on `!map.IsEmpty && protection == ProtectionMode.WhenEditable`. Passwordless by design (determinism + no real security either way). Immediately after, gated additionally on `map.HasHtmlField` (any `Html`-kind entry, recursing into collection element maps), the document-level list and style parts are seeded: `WordNumbering.EnsureListDefinitions` (bullet + decimal) and `WordStyles.EnsureStyleDefinitions` (`Normal`, `Heading1`–`Heading6`, `ListParagraph`). Word can only apply a list or a named style against a pre-existing definition — creating one writes the document-level `numbering.xml` / `styles.xml`, which read-only protection locks — so without the seed the list buttons and style gallery are greyed out inside an otherwise-editable rich-text block. Both use deterministic rel ids (`rNumbering` / `rStyles`, byte-reproducible) and are idempotent: a definition the template already carries (matched by numbering format / by `w:styleId`) is left alone. The bid export template is code-built with no styles part, so both seeds fire; the test fixture (`DocxTemplateBuilder`) ships a full styles part, so the style seed is a no-op there — `HtmlEditableSeedsStyleDefinitions` strips the fixture's styles part to observe it.
4. `ScopeTreeRunner` dispatch order: Excelsior → Format → **Editable** → StringList → Fluid. `TryResolveEditable` returns an internal `EditableToken`; `ProcessSubstitutionAsync` builds the `[permStart, sdt, permEnd]` triple via `EditableFieldBuilder` (sdtPr: site rPr clone, alias, tag = dotted path, sequential id from `EditableState`, `sdtLocked`, kind element; canonical values: `w14:checked`, `w:fullDate`, `w:listItem`) and splices via `EditableSplicer`.
   - **Temporal kinds split.** `DateOnly`/`DateTime` → `Date` kind = native date picker with canonical `w:fullDate` (no display-text parse). `DateTimeOffset` → `DateTimeOffset` kind and `TimeOnly` → `Time` kind, both **plain `w:text` controls** carrying round-trippable ISO run text — because `w:fullDate` is a bare `DateTime` (no offset) and Word has no time-only picker, so the run text is the only faithful carrier. `EditableFieldReader.ReadDateTimeOffset`/`ReadTime` parse it back offset-preserving. `EditableFieldKind.MapKind` (runtime) and `MapEditableKind` (SG) must agree on this split — both list `DateTimeOffset`/`Time` and both live in lockstep with the two `EditableFieldKind` enum copies (runtime `Parchment.Generated`, SG mirror). The old code mapped `DateTimeOffset` onto the date picker and zeroed the offset on extract — regression-guarded by `ExtractTests.TemporalTypesRoundTrip` / `EditedDateTimeOffsetPreservesNewOffset`.
   - **Editable HTML (`Html` kind).** A `string` also marked `[Html]`/`[StringSyntax("html")]` maps to `EditableFieldKind.Html`. `FormatMap.Build` skips it (the editable map claims it — same skip must exist on the SG side). `ProcessSubstitutionAsync` does **not** inline-splice: `QueueEditableHtml` renders the value through `OpenXmlHtml.WordHtmlConverter.ToElements` and `EditableHtmlBuilder` wraps the produced blocks in a **block-level** `[permStart, SdtBlock(sdtLocked, tag = path), permEnd]` triple (the block analogue of `EditableFieldBuilder`; a rich-text control has no kind element). It must sit solo in its paragraph (own-paragraph rule, like read-only `[Html]`) — enforced at render, not registration. `[Markdown]` + editable stays rejected — extraction has no OpenXML→Markdown serializer.
5. **Body-only**: `RegisteredDocxTemplate.RenderPartAsync` passes `EditableMap.Empty` for non-body parts — header/footer occurrences render as plain read-only mirrors. `ProcessLoopAsync`'s cloned runner also gets `EditableMap.Empty` (per-iteration controls would duplicate tags); if-branch inner runners keep the real map.

**Extraction** (`src/Parchment/Extraction/`): `ParchmentExtractor.Extract<T>` opens read-only, matches `body.Descendants<SdtElement>()` tags against the map (per-type cached — Extract is per-request), reads per kind via `EditableFieldReader`, reports `FieldState` per field (`Extracted`/`Empty`/`Missing`/`ParseFailed`/`Duplicate` — first occurrence wins). A text box is stored twice, as a DrawingML shape in `mc:Choice` and as VML in `mc:Fallback`, so a token typed once into a box is scanned twice and rendered as a control in each copy. The pair is one use: `EditableTokenValidator` and `ValidateEditableTokens` leave the fallback copy out of the duplicate count, and both extraction passes and the per-item control lookup skip every control under an `mc:Fallback` (`ParchmentExtractor.InFallback`), because Word edits the choice. Counting one and not skipping the other brings back either the registration failure or a `Duplicate` field. Tests: `EditableTextBoxTests`. `ExtractResult.ApplyTo` validates `CanReach` for every applicable field **before** mutating anything, then assigns; `Empty` → null for nullable members only. Editable display text is always written invariantly (Fluid's `TemplateOptions.CultureInfo` defaults to invariant and `SharedFluid` doesn't override it), so `EditableFieldReader` parses numerics and the text-backed temporal kinds with the invariant culture and the rendered format **first** and only then with `Extract`'s `culture` — an unedited document must extract the rendered values under any culture. Numerics are parsed without `AllowThousands` in both passes: with group separators allowed, `12,5` reads as 125 invariantly and the rendered `12.5` reads as 125 under `de-DE`; without them a text has one reading at most. The `Html` kind reads via `OpenXmlHtmlSerializer.ToHtml(sdtContent, mainPart)` — the reverse of `WordHtmlConverter`, walking **standard** OOXML (pStyle headings, `w:numPr` lists resolved through the numbering part, run `rPr` emphasis, hyperlink rels) so it inverts both the render and Word's own edits; subset = `p`/`h1`–`h6`/`strong`/`em`/`u`/`s`/`sup`/`sub`/`a`/`br`/`ul`/`ol`, anything else degrades to text. An `ol` gets `start` from the numbering instance's `w:lvlOverride` for its level, else the definition level's `w:start`, and only when that is not 1: OpenXmlHtml writes a start override of 1 on every ordered list, so 1 means no attribute. A second paragraph inside an `li` does **not** round-trip: OpenXmlHtml writes it as a bare `w:p` with no numbering, indent or style, so after the last item it is identical to a paragraph following the list and the serializer has nothing to recognise. `EmitList` keeps one open list per depth, so any `w:ilvl` sequence nests validly: a skipped level (0 to 2, or a list starting indented) gets a list holding an empty `<li>`, which renders back to the same levels. `WordHtmlConverter` draws an element's default look as **direct** run properties (`w:b` on every heading run, `w:u` plus the link colour on every link run), so the serializer treats those as implied by the `h1`–`h6` / `a` it emits rather than as `strong` / `u` — otherwise an unedited field is not a fixed point. Only a departure is reported, in the form the converter reads back: `<span style="font-weight:normal">` for an explicit `w:b w:val="0"` in a heading (a missing `w:b` is what applying a heading style in Word leaves, so it stays implied), and `style="text-decoration:none"` on an `a` whose runs are not all underlined (direct `w:u`, or the `Hyperlink` run style Word's own links use). Because it needs the numbering/hyperlink parts, `EditableFieldReader.Read` takes `MainDocumentPart`. Which paragraphs and runs a control holds is decided in one place, `EditableContent`, for both `RawText` and the serializer: it descends through every wrapper by default (nested `w:sdt`, `w:fldSimple`, `w:smartTag`, `w:dir`/`w:bdo`, `w:customXml`, text boxes) and names only what it skips, which is the accepted view of tracked changes (`w:del`, `w:moveFrom`, a deleted row, an emptied paragraph whose mark is deleted) and all but the first branch of `mc:AlternateContent`. Neither reader should walk `Elements()` or `Descendants()` of a control itself. Tests: `EditableFieldTests.HtmlEditableReadsThrough*`, `ExtractTests.PlainFieldReadsThroughWhatWordWrapsRunsIn`.

**SG path** (`src/Parchment.SourceGenerator/`):

1. `ShapeBuilder` detects `Parchment.EditableFieldAttribute` via typed symbol (`GetTypeByMetadataName`, like Excelsior), reads `MultiLine`/`DateFormat` named args, maps the kind from the symbol (`EditableKindFor`/`MapEditableKind` — lockstep with runtime `EditableMap`; `[Html]`+string → `Html` kind, and `AccessorEmission` keeps such members out of `_Formats`, mirroring `FormatMap.Build`'s editable skip), and bakes primitives into `MemberEntry` (`IsEditable`, `EditableKind?`, `EditableIsNullable`, `HasUsableSetter`, `EditableMultiLine`, `EditableDateFormat`).
2. `ValidateEditableShape` fires PARCH013/014/015 per offending member whether or not a token references it — lockstep with `EditableMap.Build` throwing unconditionally at docx registration. PARCH015 now fires only for `[ExcelsiorTable]`/`[Markdown]` + editable; `[Html]` + editable is valid. Docx and bindable targets only; the markdown flow never builds the map, so markdown targets stay silent. The shape rules that are not about editable fields (PARCH019, PARCH023, PARCH025, PARCH026) live in `ValidateShape`, which all three of `ProcessDocx`, `ProcessMarkdown` and `ProcessBindable` call: they describe what `AccessorEmission` does with a member, and that pass is the same for every flow. A new member-shape rule belongs there unless it is editable-specific.
3. Token rules run in a **separate body-scoped pass** (`ValidateEditableTokens`): `DocxArchiveReader`/`DocxData` carry `BodyParagraphs` alongside the all-parts list (zip entry order isn't body-first, so the body part is tracked explicitly). The pass tracks loop scope silently (no PARCH001/005 re-reports) and emits PARCH016 (non-plain), PARCH017 (duplicate in body — header mirrors don't count, nor does the `mc:Fallback` copy of a text box, flagged per paragraph by `DocxData.BodyFallbacks`), PARCH018 warning (any editable-resolved token inside a `{% for %}` body that renders read-only, root-pathed or loop-var-pathed). PARCH016/PARCH017 apply to the tokens that render as controls — a root member outside every loop, and an item member through the loop variable directly inside a top-level editable-collection loop (duplicates counted per loop) — and PARCH018 to the rest; an editable collection's own token (`{{ Lines | size }}`) is not a field and gets none of them.
4. `AccessorEmission` emits the fifth dataset `_Editables` (`EditableFieldMapEntry`: path, kind, `typeof(underlying)`, nullability, getter, block-bodied parent-routed setter with nullability-aware cast — `(decimal?)v` vs `(string)v!` — and `CanReach` lambda) registered via `GeneratedRegistration.RegisterEditable`. Invalid members (kind null / no setter) are skipped so emitted source stays compilable; the error diagnostic fails the build anyway.
5. `[ParchmentModel(Protection = ...)]` arrives as the enum's underlying int (SG can't reference Parchment.dll), lands on `TargetInfo` as the SG-side `ProtectionMode`, and is emitted as a third `RegisterDocxTemplate` argument **only when non-default** — keeping pre-existing generated output (and snapshots) byte-identical.

**Lockstep**: runtime `EditableMap` walk/rules ↔ `ShapeBuilder`+`ValidateEditableShape`; runtime `EditableTokenValidator` ↔ `ValidateEditableTokens`; runtime `EditableMap.BuildSetter` parent-routing ↔ `AccessorEmission.EmitSetter`. Tighten in the same PR. Tests: `EditableFieldTests` + `ExtractTests` (runtime), `EditableFieldGeneratorTests` (SG). Scenario: `src/Parchment.Tests/Scenarios/editable-fields/`.

### Editable collections (repeating sections) (`[EditableField]` on a collection)

A `List<T>` / `T[]` / `IList<T>` of a POCO element type, marked `[EditableField]`, renders as a Word repeating section (`w15:repeatingSection` = `DocumentFormat.OpenXml.Office2013.Word.SdtRepeatedSection`). User-facing docs in `readme.md` → "Editable collections". Files: `src/Parchment/Editable/CollectionEntry.cs`, `EditableRepeatingBuilder.cs`, `Extraction/ExtractedCollection.cs`.

1. **Map.** `EditableMap.Build` descends an editable collection (`TryGetElementType` + `ShouldDescend`) into a `CollectionEntry` — dotted path, element type, collection setter, `CanReach`, `ElementFactory` (`Activator.CreateInstance`), `IsArray`, and an `ElementMap = Build(elementType)` (item-relative sub-entries). Throws at registration on: element with no parameterless ctor, element with no editable members, non-settable collection member, or a nested editable collection (one level only). A system element type (`List<string>`) is **not** a collection here — it falls through to the scalar path → `PARCH013`; model scalar collections by wrapping the value in a single-field element type.
2. **Render.** `ScopeTreeRunner.ProcessLoopAsync` matches the loop source path (`IdentifierVisitor.Collect(loop.LoopSource)[0].Dotted`) against `editables.TryGetCollection`. A hit also needs `HasItemControl` — a token for an editable member of the item among the loop's own tokens (through conditionals, not nested loops); a loop with none stays an ordinary read-only loop, which is what lets a template list the collection a second time. On a hit, `RenderEditableCollection` renders one `w15:repeatingSectionItem` per model item with a per-item map (`EditableMap.ScopedToItem` — re-keys the element map under the loop variable and binds getters to the item; control tags stay item-relative), then wraps the items in the container (tag = collection path) inside one `permStart`/`permEnd` range via `EditableRepeatingBuilder`. Inner controls' own perm markers are **stripped** (the container range covers them, and per-item perm ids would collide when Word clones a row). Empty collection → one blank item so Word has a clone template. Its controls are built from **no item** (`ScopedToItem(loopVariable, null)`, every getter null) and so show placeholder text: built from a default element, a non-nullable member would render `0` / a date / the first enum name, which extraction reads as a value. The loop variable is still bound to a default element for the tokens that are not editable fields. A checkbox cannot be empty, so the blank item also carries `w:tag="parchment-blank-item"` (`EditableRepeatingBuilder.BlankItemTag`). Body-only, like scalar fields.
3. **Extraction.** `ParchmentExtractor` runs a repeating-section pass **before** the flat scalar pass: locate `SdtRepeatedSection` by tag, read each item's item-relative controls via `EditableFieldReader`, reconstruct `new TItem()`, drop all-empty items, build `List<TItem>`/`TItem[]`. A new item has no nested objects, so the **element-rooted setter creates the parents** of a nested member (`AccessorEmission.EmitCreatingSetter`, per hop where `MemberEntry.CanCreateValue`: an assignable member whose type is a concrete class with a public parameterless constructor); the root-level setter never does, since `ApplyTo` is handed a model the caller built. The extractor calls the setter and only then asks `CanReach`: still false means a hop could not be created, reported by giving that row's entry for the member in `Fields` the state `FieldState.Unreachable`, which makes `AllExtracted` false. "Empty" is decided per control, never by comparing the item with a default element — a row rendered from a real item whose values are all defaults has to come back. The one exception is an unchecked checkbox, which cannot show emptiness and so does not count as a value in a row known not to be a rendered item: the item tagged `parchment-blank-item` (an item rendered from the model never carries that tag, and Word copies it onto rows added from it), or a row holding a control Word reset. Word's "+" copies a row and resets each control that held a value to a `w:showingPlcHdr` placeholder of spaces, where the render's own placeholders are words (`Enter text`), so a row added and left alone is dropped while a rendered item whose only value is `false` is kept. A row added from a rendered row that held no values at all copies the render's placeholders and cannot be told from it, so that one is kept. Each kept row's per-member outcomes are appended to `ExtractResult.Fields` under `Collection[index].Member` (index = position in the rebuilt list; a dropped row reports nothing), with an absent control as `Missing`, so `AllExtracted` covers rows; a `ParseFailed` control counts as content and keeps the row. Those paths match no map entry, so `ApplyTo`'s scalar loop skips them. The flat pass skips every control that has a repeated-section item above it (`RepeatedItemOf`), whichever section that is — row tags are bare member names, which repeat across items and can equal a root member's path — and a row reads only the controls whose nearest item is that row. The extractor keeps each kept row as values only; `ExtractResult.ApplyTo` builds the list and its items from them on every call (so two models applied from one result share neither) and assigns it — **replace-all**; identity-preserving callers diff it themselves.
4. **SG.** `MemberEntry.EditableCollectionElementFqn` marks editable collections (`EditableKind` stays null); `AccessorEmission` emits the `_EditableCollections` dataset (`CollectionFieldMapEntry` with element-rooted sub-entry getters/setters via a nested `WalkForMaps`) registered through `GeneratedRegistration.RegisterEditableCollections`. `EditableMap.RegisterPrecompiled` / `RegisterPrecompiledCollections` **merge** into the per-type cache (order-independent). `ValidateEditableShape` skips `PARCH013` for editable collections (guards only the collection setter → `PARCH014`); `ValidateEditableTokens` lifts `PARCH018` for the loop-variable tokens directly inside a top-level loop whose source is an editable collection, and holds them to `PARCH016`/`PARCH017` instead.
5. **One binding.** Extraction reads the first repeating section tagged with the collection path and the first control per member in a row, so `EditableTokenValidator.Validate` throws, and `ValidateEditableTokens` reports `PARCH017`, for a second token of one item member in the loop and for a second top-level body loop holding any item control. Both use the definition of a control that `HasItemControl` renders by (`CollectionEntry.TryGetItemEntry` at runtime).
6. **No loop modifiers.** `limit:` / `offset:` / `reversed` on a repeating-section loop would make replace-all extraction write the window (or the reversed order) back as the collection, so `EditableTokenValidator` throws and `ValidateEditableTokens` reports `PARCH027`. Both scope the rule to a top-level body loop — a nested loop or a non-body part renders read-only and applies the modifier.
5. **Protection: `readOnly`, not forms.** The repeating section works under `edit="readOnly"` (validated in Word) because it sits in a perm range — `SettingsProtection` is unchanged. `edit="forms"` would also allow add/remove but blocks selecting/copying the locked text, so `readOnly` is retained.

**Lockstep**: `CollectionEntry` build/constraints ↔ `ShapeBuilder` collection detection + `ValidateEditableShape`; `RenderEditableCollection` ↔ `AccessorEmission` collection emission; `RegisterPrecompiledCollections` ↔ the `CollectionFieldMapEntry` carrier. Tests: `EditableCollectionTests` + `DeterminismTests.EditableCollectionRenderIsByteIdentical` (runtime), `EditableFieldGeneratorTests.EditableCollection_*` (SG).

### Validation topology — four validators that must agree

The same template is validated by four separate implementations, and they validate the *same* templates against the *same* model. Any disagreement is a bug, and the direction matters: the source generator's diagnostics are `Error`, so a template the runtime accepts but the generator rejects fails the build outright.

| path | entry point |
|---|---|
| markdown, runtime | `Liquid/MarkdownReferenceValidator` (Fluid AST walk, scope + `untyped` set) |
| docx, runtime | `Tokens/TokenScanner` → `ScopeTreeBuilder` → `ReferenceValidator` |
| markdown, source generator | `Parchment.SourceGenerator/MarkdownValidator` |
| docx, source generator | `ParchmentTemplateGenerator.ValidateTokens` |

**Lockstep**: the `untyped` set in `MarkdownReferenceValidator` ↔ the one in `MarkdownValidator` — `forloop` scoped to a loop body, `tablerowloop` scoped to a `{% tablerow %}` body (which does not set `forloop`), `{% assign %}` / `{% capture %}` targets, and a loop variable whose source has no static member path. Both walk the same statement kinds; `MarkdownBlockTagCases` is one list of templates compiled into both test projects (`MarkdownBlockTagTests`, `MarkdownBlockTagGeneratorTests`), so a verdict cannot be pinned for one and not the other. Loop-source resolution ↔ `ShapeResolver.TryGetElementType`. When tightening one, check the other three.

**Lockstep**: a loop variable wins over a root member of the same spelling. The attribute maps are keyed on dotted paths from the root, and inside `{% for customer in Customers %}` the token `{{ customer.Notes }}` spells the root path `Customer.Notes` while reading the loop item. Every consumer of a root-keyed map therefore asks first whether the token starts with a loop variable in scope: `LoopScope` for the docx flow (`ScopeTreeRunner` carries the open variables into each nested runner; the three token validators track them over the flat classification list), `MarkdownLoopScope` for the two registration-time rewrites, which work on source text and so measure a loop by its position. The generator resolves through `ShapeResolver` with a scope, except `ValidateMarkdownExcelsiorTokens`, which reads source text and carries its own copies of `MarkdownLoopScope` and `MarkdownOutputTokens`. A loop's extent ends at its own `{% else %}`, not at its `{% endfor %}`: Fluid renders the else branch when nothing was iterated, without binding the variable, so `MarkdownLoopScope` stops there and the two AST validators (`MarkdownReferenceValidator`, `MarkdownValidator`) walk the branch in the enclosing scope. `MarkdownLoopScope` also records the `{% raw %}`, `{% comment %}` and inline `{% # %}` regions (`IsLiteral`): a tag inside one opens or closes nothing, and what reads as a token there is neither rewritten nor checked by the source-text readers — the AST validators never see it, since Fluid parses those regions to text. Its rules for a mapped member (`PARCH007` / `PARCH008` / `PARCH010`) are gated on `ShapeResolver.TryResolveMappedMember`, which walks from the root through instance members only, as the map walkers do: a token rooted at a loop variable or passing through a static member reaches an annotated member the maps do not hold, so it is an ordinary Fluid value and may share its paragraph and take a filter. `PARCH024` is reported for a bare output path alone — with a filter the token is the author's own expression, and `| html` / `| markdown` is the remedy that diagnostic names. The comparison is ordinal, matching Fluid: a loop variable is found by exact spelling, a model member without regard to case, so `{{ Customer.Notes }}` inside that loop is still the root member. `TryResolveEditable` is the one lookup with no check — a runner inside a loop never holds a root-keyed editable map, and `EditableMap.ScopedToItem` keys its entries under the loop variable on purpose.

**Lockstep, liquid members**: a string, a dictionary and anything else enumerable never reach a template as an object — `FluidValue.Create` wraps them as `StringValue` / `DictionaryValue` / `ArrayValue`, and the wrapper answers member access itself, ordinally: `size` on all three, `first` / `last` on a string or an array, nothing else (a dictionary treats any other name as a key). Their CLR members (`Count`, `Length`, a property of a model's own collection class) render blank, so every segment past the root resolves through `Liquid/LiquidMembers` (runtime, via `ModelValidator.TryResolveSegment`) ↔ `ShapeBuilder.LiquidKindFor` + `ShapeResolver.TryResolveLiquidMember` (SG, keyed off `TypeEntry.Liquid`) instead of by reflection or `MemberEntry`. The classification reads the *declared* type and tests dictionary before enumerable, as Fluid does. The root is the exception, and only because the render makes it one: `TemplateContext` would run a model that is itself a collection (`class Order : List<Line>`) through the same `FluidValue.Create`, so `SharedFluid.CreateContext` hands it over as an `ObjectValue` and the members the model declares bind through its accessors — every render context has to be built there. Fluid falls back to reflection for the model type, which would also bind what the collection base declares (`Count`, `Keys`); the generator emits and resolves none of that, so `ModelValidator.TryResolveRootMember` rejects a root name declared by a system type on such a model ↔ the base-chain stop in `ShapeBuilder.BuildEntry`. Tests: `EnumerableModelTests` ↔ `EnumerableModelGeneratorTests`. Tests for the rest: `LiquidMemberTests` (runtime, including a pin that Fluid binds none of the rejected names) and `LiquidMemberGeneratorTests` (SG) run the same paths.

**Lockstep, one member per name**: a name can be answered by more than one member — a `new` member hiding a base one of another type, or two members whose names differ only by case — and both are legal C#. `ShapeBuilder` walks the most derived type first and each type in declaration order, keeping the first member per name (compared `OrdinalIgnoreCase`), so that member is the only one with an accessor and every spelling validates against its type. `ModelValidator.TryResolveMember` (runtime) walks the same order by hand; a case-insensitive `GetProperty` / `GetField` throws `AmbiguousMatchException` on such a type and also skips a base type's static members. Metadata keeps properties and fields in separate tables, so a property is placed against a field through its backing field; a computed property has none and is taken to come first, the one case the two sides can disagree. Tests: `AmbiguousMemberTests` (runtime) and `AmbiguousMemberGeneratorTests`.

**Lockstep, dictionary entries**: all four validators bind the variable of a loop over a dictionary to `KeyValuePair<K, V>` (`Key`, `Value`), but enumerating Fluid's `DictionaryValue` yields a two-element `ArrayValue` per entry, so the pair and the accessors emitted for it never reach the template. `Liquid/DictionaryLoops` closes the gap at the value: a converter on both option sets wraps the `DictionaryValue` Fluid makes, and the wrapper's entries answer `Key` / `Value` (any case, dotted or bracketed) and delegate everything else to the array, so `kv[0]`, `kv[1]`, `kv.first` and `kv.last` still render. It has to be the value and not the docx loop runner, because the markdown flow iterates through Fluid's own `for`. The validators keep rejecting `kv.first` / `kv.last`: the same `KeyValuePair` type also reaches a template as a plain object (a `List<KeyValuePair<K, V>>`), where the array names bind nothing. The converter takes only what Fluid makes a dictionary of; Fluid converts a list's items while wrapping the list, so letting a list through the converter's nested call would leave a dictionary inside it unwrapped. A dictionary with non-string keys is unchanged: Fluid skips every such key, so the loop has no iterations. Tests: `DictionaryLoopTests`.

**Lockstep, system types**: `ShapeBuilder` records no members for a type whose outermost namespace is `System` (`IsSystemType`), `KeyValuePair<K, V>` excepted, so no accessor exists for one and its members render blank although reflection finds them: `Year` on a `DateTime`, `Value` / `HasValue` on a `Nullable<T>`, `Item1` on a `ValueTuple` or a `Tuple`, `MaxValue` on an `int`, a constant of a system enum. `ModelValidator.TryResolveSegment` asks `HasNoAccessors` before it reflects, and after the liquid classification, which is the order `ShapeResolver.TryResolve` arrives at from a `TypeEntry` without members. A nullable struct of the model's own is a `Nullable<T>` too: the generator never reaches the struct through it, so `{{ Meta.Name }}` on a `Meta?` is rejected on all four paths. Nothing names the model either: Fluid resolves a `model.` or type-name prefix to nil, so it is an unknown root on all four paths (`ModelValidator.TryResolveRoot`, `PARCH001`) and not an alias for the model. Tests: `SystemTypeMemberTests` (runtime, with the same Fluid pin) and `SystemTypeMemberGeneratorTests` (SG) run the same paths.

**Lockstep, enums**: an enum is the same case by another route — the value converter in `SharedFluid.BuildOptions` hands it to Fluid as a `StringValue` of the text it prints as, a nullable enum included, since it is boxed on the way. Its constants are public static fields to reflection and to Roslyn alike, so a path through one used to validate everywhere and then render blank. `LiquidKind.Enum` resolves no member at all on both sides, and `ShapeBuilder` records none, which is also what keeps `AccessorEmission` from emitting an accessor per constant. `size` / `first` / `last` would bind on the text, but the length of a display label is not model data, so they stay rejected. The generator reports through a second `PARCH001` descriptor (`Diagnostics.UnknownMember` picks between the two), since "not a member" about a constant that is plainly there in the C# reads as a spelling mistake. Tests: `EnumMemberTests` (runtime) and `EnumMemberGeneratorTests` (SG) run the same paths.

**Lockstep, token values**: a member declared as `TokenValue` or anything derived from it (`HtmlToken`, `MarkdownToken`, `OpenXmlToken`, `MutateToken`, a token type of the model's own) is printed, never read. The markdown flow's value converter hands Fluid the text the token renders as, so `{{ Body.Source }}` is nil there, while the docx flow keeps the object and printed raw markup, or the type name of a delegate. `ModelValidator.TryResolveSegment` resolves no segment past a token ↔ `ShapeBuilder` records no members for one (`IsTokenValue`), which also keeps `AccessorEmission` from emitting an accessor per token property. Nothing internal reads a token through liquid: the renderers take `Source` / `Render` / `Apply` off the C# object. Tests: `TokenValueMemberTests` (runtime) and `TokenValueMemberGeneratorTests` (SG) run the same paths; the token stubs in the generator tests' `GeneratorDriver` carry the real public members for that reason.

Known and deliberate asymmetries, so they are not "fixed" into divergence:

- The docx flow runs its own scope tree rather than liquid's `{% for %}`, so it never populates `forloop`, and `assign` / `capture` are not among its block tags (`for`, `endfor`, `if`, `elsif`, `else`, `endif`). Registration says so rather than rendering a blank.
- A loop source that resolves to a real type which is not enumerable is a mistake and throws on all paths. One that does not resolve at all — a range, an assign target — is an unknown, and the loop variable is accepted as untyped. A range is recognised by its shape (a source that is not a member path), never by having no references: `(1..Count)` names a member, and that member is a bound to validate, not the thing iterated. The two docx validators have no `untyped` set; each binds such a loop variable to a sentinel in its scope (`ReferenceValidator.untyped`, `ParchmentTemplateGenerator.untypedLoopVariable`), which keeps shadowing and restore on `endfor` on the one code path.
- `{% render %}` / `{% include %}` are rejected on all four paths, by different means. The docx flow rejects every tag outside its list. The markdown flow accepts whatever Fluid parses, and these two parse and then load a partial through `TemplateOptions.FileProvider`, which nothing sets — a `FileNotFoundException` at render. `MarkdownReferenceValidator` throws from `VisitIncludeStatement` / `VisitRenderStatement`; `MarkdownValidator` reports `PARCH003` from a visitor of its own (`PartialTagCollector`), because its reference walk does not descend into every statement.
- `{% liquid %}` is rejected on all four paths, by different means. The docx flow rejects every tag outside its list. In the markdown flow Fluid (2.40) registers the tag and does not run it: one statement parses to no statement and swallows the rest of the template, several are a parse error, so nothing is left in the tree to validate. `MarkdownFluidParser` (one copy per project) re-registers the tag to read to its own `%}` and leave an `UnsupportedLiquidTagStatement`; `MarkdownReferenceValidator.VisitOtherStatement` throws on it and `MarkdownValidator` reports `PARCH003` from a visitor of its own (`LiquidTagCounter`), because its reference walk does not descend into every statement. `{% echo %}` as a tag of its own is an ordinary `OutputStatement` and is validated like `{{ }}`; the `[Html]` / `[Markdown]` / Excelsior rewrites match `{{ }}` source text only, so an echoed member renders as escaped text. Retest before lifting the rejection on a Fluid upgrade.
- A filtered source (`{% for x in Src | filter %}`) never reaches any validator: Fluid rejects it as an invalid `for` tag.
- A member declared as `TokenValue` is an object with no members to all four validators, and not a loop source, even though a render that finds text in it hands Fluid a string, which answers `size` / `first` / `last`. Those hold only while the value is text: markup stays an object in the docx flow and renders them blank, so classifying `TokenValue` as a liquid string would register templates that go blank on the next render. Tests: `TokenValueTextTests` (runtime) and `LiquidMemberGeneratorTests` (SG).
- `limit:` / `offset:` expressions are validated by the two docx paths only, against the scope *enclosing* the loop, since they are evaluated before the loop variable is bound. Neither markdown validator visits them on a `for`: both override the `for` walk and descend into the source and the body alone. On a `{% tablerow %}` both do visit `limit:`, `offset:` and `cols:`, against the enclosing scope. `offset: continue` is markdown-only: it reads a counter liquid keeps in its own loop scope, so the docx runtime rejects it in `TokenScanner` and the docx generator reports the `continue` identifier as `PARCH001`.
- A filter after `markdown`, `bullet_list` or `numbered_list` is refused by the two docx paths (`TokenScanner.ParseSubstitution` on both sides) and accepted by the two markdown ones (`MarkdownReferenceValidator.VisitFilterExpression` ↔ `MarkdownValidator.ValidateFilterOrder`), which refuse a filter after `html` alone. In a docx template all four return a `TokenValue`; in a markdown template the other three return source with `encode: false`, and Fluid's string filters carry that flag through, so `{{ Notes | markdown | upcase }}` renders there. A markdown template's headers and footers come from its style source and are scanned by the docx `TokenScanner`, so they take the docx form. The rule reads one expression, so a marker that reaches a filter another way is not caught: `{% assign x = Body | html %}{{ x | upcase }}`, a capture holding one, or a filter applied to a member typed as a token.

### Determinism guarantee

See `readme.md` → "Determinism". Implementation discipline: avoid `w:rsid` randomness, never set `PackageProperties.Created`, no timestamps. Editable fields: sequential sdt/perm-range ids (`EditableState`, seeded at registration with the highest `w:sdt` / `w:permStart` / `w:permEnd` id in any part of the template, since those ids are unique across the whole document and a template can carry content controls and editable ranges of its own), passwordless `w:documentProtection` (a password would need a random salt). `DeterminismTests.cs` renders samples twice (including scalar and HTML editable-field cases, the latter with a list) and asserts byte equality — don't break it. This relies on **OpenXmlHtml 1.0.6+** pinning the numbering part's relationship id; earlier versions drew a random one, so a list rendered into a template lacking a numbering part was non-deterministic.

**Date tokens never read `TimeZoneInfo.Local`** (`SharedFluid.BuildOptions`). Fluid holds every date as a `DateTimeOffset`, built through the implicit `DateTime` conversion, which reads `Kind` `Unspecified` as machine-local; and `TemplateOptions.TimeZone` defaults to the local zone for string and unix-timestamp inputs to `date`. A value converter pins an Unspecified value to offset zero and the option is set to UTC. `Kind` `Local` and `"now"` are left machine-dependent and documented as such. `DateTimeTokenTests` swaps the process-wide local zone through reflection on `TimeZoneInfo`'s private cache, so those tests are `[NotInParallel]`; a test that has to prove zone independence belongs there, since a CI machine set to UTC cannot tell the difference otherwise.

**Relationship ids are always explicit** (`Word/RelationshipIds.cs`). A part or relationship added without an id — `AddNewPart<T>()`, `AddImagePart(type)`, `AddHyperlinkRelationship(uri, true)`, `AddCoreFilePropertiesPart()` — is given a random one by the Open XML SDK (`R` + 16 hex digits), which lands in the `.rels` file and in the XML referencing it. Every add goes through `RelationshipIds` instead: `Named` for a part the owner holds at most one of (`rIdSettings`, `rIdNumbering`, `rIdCore`, `rIdExtended`, `rIdCustom`), `Next` for one of many (`rIdImage1`, `rIdLink1`, …), `TryHyperlink` for an external link, which also shares one relationship per target and refuses a target that is not an absolute url (the caller then writes text, matching OpenXmlHtml's `LinkTarget.TryParseAbsolute`; never hand a markdown url to `new Uri`, it throws on a bound value such as `http://`). All three check the ids the owning part already holds, because a template's own ids are arbitrary and a duplicate throws. The blank markdown style source is a fresh package, so `BuildBlankDocx` uses fixed ids directly. Verify.OpenXml rewrites relationship ids to `DeterministicIdN` before comparing, so a `.verified.docx` snapshot cannot catch a random id — only the `DeterminismTests` double renders do. Two cases escape a double render and are tested on their own: the blank style source is built once per process, and protection is written at registration. The sibling libraries name their own: Excelsior adds the styles part a template or style source lacks as `rIdStyles` and a link cell as `rIdLink<n>`, and OpenXmlHtml adds an `<a href>` as `rLink<n>`, each stepping past the ids the part already holds. Parchment therefore leaves those ids alone — renaming Excelsior's styles part afterwards would find `rIdStyles` taken by that very part and move it to `rIdStyles2`.

**Zip entry timestamps are pinned** (`Word/ZipTimestamps.cs`, called at the end of both `RegisteredDocxTemplate.Render` and `RegisteredMarkdownTemplate.Render`). Entries cloned from the registration snapshot keep their stamps through a save, but a part *added* during the render — the settings part on a markdown render whose style source has none, a numbering part for a list, an image — is stamped with the wall clock, and `[Content_Types].xml` is re-stamped on every save. Zip stores those at 2-second resolution, so before the pin two renders were byte-identical only when their saves fell inside the same 2-second window, and never across days. The double-render tests could not catch it: they render milliseconds apart and so almost always landed in the same quantum. `DeterminismTests.*PinsZipEntryTimestamps` assert the stable date directly instead.

`ZipTimestamps` patches only the four DOS time/date bytes in each local header and central directory record — no reordering, no recompression, no content rewrite. **`DeterministicIoPackaging.DeterministicPackage.Convert` was tried here and reverted**: it is built for snapshot normalization and rewrites entry *content*, which for product output loses document data — it normalizes core properties (dropping the template's own `dc:creator` that the document-properties merge exists to preserve) and its png normalizer throws on a minimal 1×1 png. The stable date matches that package's, so archives normalized by either read the same.

### Schema validation (`src/Parchment.Tests/SchemaValidationTests.cs`)

Every checked-in `.verified.docx` is run through `OpenXmlValidator` as its own test case. The render calls are spread across forty test files with no shared harness, so the snapshots — the recorded output of every flow — are what there is to hang the assertion on. Accepting a snapshot is therefore what puts a new document in front of the validator; there is no check at the point of render.

**This is the only thing in the suite that holds output to the schema.** Morph reaches for elements through the OpenXML object model, which finds a child wherever it sits inside its parent, so a document Word refuses still paginates and renders and the page snapshots agree with it. Word is stricter: it discards a whole element it finds out of place. That gap hid three defects at once — a `w:pPr` written after the runs in the first table-of-contents entry (which cost it its style and its dot leader in Word alone), `w:tblBorders` emitting `left` after `bottom`, and nested emphasis appending a second `w:i` to a run that already had one.

Element order is the trap. The OpenXML SDK's `Append` puts a child at the end regardless of where the schema declares it, so anything built by appending needs the sequence kept by hand — see `TableRenderer.BuildTableProperties`, which splits the borders and the cell margins around the table layout for exactly this reason. Where a typed property exists (`RunProperties.RunStyle`, `Paragraph.ParagraphProperties`) assigning through it places the element correctly; prefer that.

### Scenario directories (`src/Parchment.Tests/Scenarios/`)

Self-contained example folders the readme references for before/after of a feature. One subdirectory per scenario:

```
src/Parchment.Tests/Scenarios/
├── ScenarioInputRenderer.cs          # [Explicit] — regenerates all input.png files
└── <scenario-name>/
    ├── input.docx                    # committed binary — the template
    ├── input.png                     # "before" render (generated)
    ├── output.verified.docx          # Verify snapshot
    ├── output#page01.verified.png    # "after" render (Verify.OpenXml + Morph)
    └── output#00.verified.txt        # Verify text extraction
```

**Test wiring** (see `ExcelsiorTableTests.Render`):

1. `.cs` file lives under `src/Parchment.Tests/Docx/` (or wherever feature tests live), not inside the scenario dir — scenario dir is asset-only.
2. Reads `input.docx` via a `[CallerFilePath]`-anchored helper:
   ```csharp
   static string SourcePath([CallerFilePath] string path = "") => path;
   static string ScenarioPath(string name) =>
       Path.GetFullPath(Path.Combine(Path.GetDirectoryName(SourcePath()) ?? "", "..", "Scenarios", name));
   ```
3. Directs Verify into the scenario dir with a custom prefix: `settings.UseDirectory(ScenarioPath("excelsior-table"))` + `settings.UseFileName("output")` → `output.verified.docx` rather than `ClassName.MethodName.*`.

**Regenerating `input.png`**: `ScenarioInputRenderer.cs` is `[Test, Explicit]` — excluded from default runs. It globs `Scenarios/**/input.docx`, renders each via Morph/SkiaSharp, writes the first page next to the source. Invoke on demand:

```bash
    --treenode-filter "/*/*/ScenarioInputRenderer/RenderAllInputDocxesToPng"
```

`input.png` is *committed* alongside `input.docx`.

**Adding a scenario**: mkdir under `Scenarios/`, drop `input.docx` (binary already in `.gitattributes`), write a feature test that calls `UseDirectory(ScenarioPath("<name>")) + UseFileName("output")`, run `ScenarioInputRenderer` once for `input.png`, reference both PNGs from `readme.md` (note `#` → `%23` URL escape).

## Design decisions

### Source generator emits pre-compiled accessors; there is no runtime reflection fallback

User-facing summary in `readme.md` → "Source generator (recommended)". The SG is the **only** registration path for model metadata: every model reaches it, either through `[ParchmentModel]` (template by convention, embedded) or `[ParchmentBindable]` (accessors only, for templates supplied at runtime through the hand-registration API). `SharedFluid.EnsureModelRegistered` throws at registration for a model the generator never saw, and the per-template maps (`ExcelsiorTableMap` / `FormatMap` / `StringListMap` / `EditableMap`) resolve to their precompiled entries or `Empty` — the old reflection walks are deleted. Model-shape rules that used to throw from those walks are compile-time diagnostics now (PARCH013–PARCH015, PARCH019, PARCH022, PARCH023). Pattern mirrors `System.Text.Json`'s `JsonSerializerContext`, EF Core's compiled models, and the regex source generator.

Token validation is the deliberate exception: `ModelValidator` / `ReferenceValidator` / `MarkdownReferenceValidator` still reflect over the model at registration, because a runtime-supplied template was never seen by the generator and its tokens must still be checked against the model. That reflection is registration-time only and touches member *types*, not values.

**Trimming and NativeAOT.** Because of that exception and two more, the library is not NativeAOT-compatible and is not marked `IsTrimmable`. A consumer published with `PublishAot` fails registration ("Identifier 'Name' is not a member of 'Letter'", the property metadata is gone) and renders an `[ExcelsiorTable]` with an empty header and empty cells; a `PublishTrimmed` / `TrimMode=full` consumer rendered correctly when measured, with IL2104. The sites the analyzers report:

- `ModelValidator.TryResolveMember` (`GetProperty` / `GetField`) and `ModelValidator.TryResolveElementType` / `LiquidMembers.IsDictionary` (`GetInterfaces`) — token validation, IL2070.
- `EditableFieldBuilder.BuildDropDown` (`GetFields` on the enum type, for the declaration order of names sharing a value) — render time, IL2075. The class carries the attribute.
- `ExcelsiorTableBridge.CreateInvoker` (`MakeGenericMethod`) — IL2060 / IL3050. Excelsior's `WordTableBuilder<T>` then reflects over `T` for its columns, which no annotation in this repo can see.
- `ExtractedCollection.Build` (`MakeGenericType` for `List<T>`, `Array.CreateInstance`), reached through `ExtractResult.ApplyTo` — IL3050.
- `DictionaryLoops.HasStringKeys` (`GetInterfaces`) — render time, IL2070, and the one site that is suppressed instead: its converter is registered from `SharedFluid`'s static initializer, which cannot carry `[RequiresUnreferencedCode]`, and Fluid makes the same interface check before it builds a `DictionaryValue`, so a trimmed-away interface gives the answer Fluid itself acts on.

`Parchment.csproj` sets `EnableTrimAnalyzer` and `EnableAotAnalyzer` (not `IsTrimmable` / `IsAotCompatible`, which would stamp the assembly as compatible), and those sites are covered by `[RequiresUnreferencedCode]` / `[RequiresDynamicCode]` carried up to the public `TemplateStore` and `ParchmentExtractor` methods and `ExtractResult.ApplyTo`, with the messages in `Unsupported.cs`. Whole classes carry the attributes where an override or a field initializer could not (`MarkdownReferenceValidator` overrides Fluid's `AstVisitor`; the three `RegisteredTemplate` types share an abstract `Render`). A new reflection call outside such a scope is an IL warning, and so a build error, here; annotate the caller chain instead of suppressing it — `UnconditionalSuppressMessage` would hide the site from a consumer's publish. Consumers that do not publish trimmed or AOT have no analyzer running and see nothing.

**Pipeline.** `AccessorEmission.Emit(target.Shape, rootFqn)` walks `ModelShape` and produces parallel datasets:

1. **Fluid accessors**: `KeyValuePair<string, IMemberAccessor>[]` per non-empty type (one `DelegateAccessor` per public property/field), registered via `GeneratedRegistration.RegisterFluidAccessors(typeof(T), arr)` → `SharedFluid.registeredTypes` + `Options.MemberAccessStrategy.Register`. The root type's block is emitted even when member-less — its registration, together with the `[ParchmentModel]` / `[ParchmentBindable]` attribute on the type, is what marks the model SG-known to `EnsureModelRegistered`. The attribute check is there because a type reached only as a member gets an accessor block too, but none of the per-model maps below: registered as a model it would render with its `[Html]`, string-list and `[EditableField]` members ignored, so `IsModelRegistered` rejects it as it rejects a type the generator never saw.
2. **Excelsior-table entries**: dotted-path walk collecting `[ExcelsiorTable]` members as `(DottedPath, ElementType, Getter)`. Registered via `RegisterExcelsiorTable` → `ExcelsiorTableMap.precompiledCache`.
3. **Format entries**: same walk for `[Html]` / `[Markdown]` / `[StringSyntax]` strings as `(DottedPath, FormatMapKind, Getter)`. Render-time `ScopeTreeRunner.TryResolveFormatted` uses the emitted getter — no per-segment reflection.
4. **String-list entries**: dotted-path walk for `IEnumerable<string>` members not already owned by `[ExcelsiorTable]`. Populates `StringListMap.precompiledCache`. `ShapeBuilder.TryGetSequenceElementType` decides what a sequence is for this and for `[ExcelsiorTable]`: a multi-dimensional array (`string[,]`) has an element type but is no `IEnumerable<T>`, which is how the runtime reads both, so it is neither a string list nor a table source.

`KeyValuePair<K,V>` is special-cased in `ShapeBuilder` (Key/Value members surfaced, argument types enqueued) so dictionary iteration binds; array types are deliberately member-less (their CLR members are not binding surface). For the same reason the base-chain walk of a model's own collection class stops at its first system base — `class Bag : List<Line>` keeps what `Bag` declares and drops `Count` / `Capacity` — and `TryGetMemberType` never surfaces an indexer or a property without a public getter, since an accessor for either (`o.this[]`, a call to a private get) does not compile. The same goes for every other legal member no accessor can be written for: one typed as a ref struct (`ReadOnlySpan<char>`) or as, or over, a pointer or function pointer (not an `object`, or needing an unsafe context), a static abstract or virtual interface member (reachable through a type parameter only), and an inherited member whose name a more derived type reuses for a method, an event, a nested type or an unreadable property (`((Derived)o).Name` binds to that instead; accessibility is judged from the generated class, with `Compilation.IsSymbolAccessibleWithin`). `ModelValidator.TryResolveMember` rejects the same members at registration, so a token naming one fails instead of rendering blank. `dynamic` is not skipped but spelled `object` by `ShapeBuilder.Fqn` wherever it sits in a type name, since `typeof(List<dynamic>)` is CS1962 and the two are one runtime type. Emission avoids `StringBuilder.AppendJoin` — under the netstandard2.0/Polyfill analyzer build it binds to the params-object overload and stringifies the list.

**Public API surface.** SG-emitted code calls into `Parchment.Generated`:
- `GeneratedRegistration` — static class with one `Register*` method per dataset.
- `ExcelsiorTableMapEntry`, `FormatMapEntry`, `StringListMapEntry` — public data carrier records.
- `FormatMapKind` — public enum (replaces internal `FormatKind`).

These must stay public — SG runs against user assemblies, signed assembly + arbitrary user PKs means `[InternalsVisibleTo]` won't help. The maps themselves (`SharedFluid`, `ExcelsiorTableMap`, etc.) stay internal.

**Path-getter emission.** Cast-and-null-chain lambdas: `o => ((global::NS.Root)o).First?.Second?.Third`. Root cast unconditional (`Render` rejects null models); subsequent segments use `?.` to match runtime `ChainGetter` null-short-circuit. Non-nullable value-type intermediates would fail to compile — accepted for the read-only maps (`[ExcelsiorTable]`, `[Html]`/`[Markdown]`, string lists), since binding-model intermediates are virtually always reference types. Editable members are the exception, because a setter through a struct is wrong as well as uncompilable (it assigns to a copy, and `((Struct)o).X = v` is CS0445): `WalkForMaps` carries the first struct met on the path (`TypeEntry.IsValueType`) and leaves out every editable member below it, and `ValidateEditableShape` reports the same list as `PARCH032` through `AccessorEmission.EditablesThroughValueType`, which runs that same walk. A struct element type of an editable collection is `PARCH022`. A `Nullable<T>` struct is a system type to the shape, so its members are never walked.

**Tests.** `Parchment.Tests` (runtime — its models carry `[ParchmentBindable]` and the SG runs over the test project itself), `Parchment.SourceGenerator.Tests` (SG snapshots), `IntegrationTests` (SG output against packed nupkg).

### `[ParchmentModel]` lives on the binding model, not on an intermediary "template" class

Full rationale and alternatives in `readme.md` → "Source generator (recommended)". Implementation-relevant points:

- The attribute target IS the model; no separate marker class, no arguments — the template is the AdditionalFile named after the type.
- Model must be `partial` (SG emits the embedded template + module initializer onto it). PARCH011 fires when nested inside a non-partial enclosing type; PARCH031 when the declaration is generic, file-local, or nested inside either (`FindUnsupportedDeclaration`), since no generated partial can register those. A module initializer must be reachable from the module (CS8814), so for a `private` / `protected` nested model, or a model inside one, the registration stays in the model and `BuildPartialSource` emits a forwarding method into each enclosing type above a private level; the outermost carries `[ModuleInitializer]`.
- `[AttributeUsage(AttributeTargets.Class)]` blocks interface targets (CS0592). Runtime interface guard: `GuardBindingModel` in `TemplateStore.cs`.
- One template per model is now structural: the store is keyed by `Type`, `Render<TModel>` is the whole render surface, and `Resolve` walks the base chain so an abstract-base registration accepts subclass instances. Dynamic-template scenarios use the runtime `TemplateStore.RegisterDocxTemplate<T>` / `RegisterMarkdownTemplate<T>` overloads with a `[ParchmentBindable]` model — keep them as the supported escape hatch for the template side; there is no path for a model the generator never saw.
- When touching `ParchmentTemplateGenerator.cs`, the attribute predicate, target shape, `BuildPartialSource` wrapping, and any new diagnostics all treat the attribute target as the model type. No second symbol to thread through.

### Equal table column widths are deliberately inexpressible

`TableRenderer.ComputeColumnWidths` reads relative widths from the dash counts in a pipe table's separator row, and ignores them in two cases: no width hints at all (`totalPct == 0`), and every column carrying the same count (`allEqual`). `OpenXmlMarkdownRenderer.SkipColumnWidths` filters a third upstream — source-aligned tables, where the dashes are padded so the markdown lines up. All three mean "no opinion on widths", so the table is left on Word's autofit and sizes to content.

The cost is that genuinely equal columns cannot be stated. Equal dash counts are indistinguishable from `| --- | --- |`, which is how nearly everyone writes a separator regardless of intent.

**Removing the `allEqual` check was tried and reverted.** It is not redundant with `SkipColumnWidths`: that one catches source-aligned tables, `allEqual` catches uniform-but-unaligned ones. Dropping it regresses the most common table shape in the corpus from content-sized to equal fixed columns. No dash-count heuristic can separate the two intents, because they are written identically — so this is a syntax gap, not a heuristic to tune.

Expressing it needs explicit width syntax, and a table already takes a leading `{.StyleName}` on its own line as a place to carry one. Four things to settle first:

- **Syntax** — key=value on the existing generic attribute, or a dedicated one.
- **Units** — relative weights, percentages, or absolute. `w:gridCol` takes twips only, and `TableRenderer` already converts ratios against `GridWidthBudgetDxa`.
- **`MarkdownStyle` contract** — `Resolve` reads `Classes.FirstOrDefault()` and deliberately discards `#id`, further classes, and key=value properties, documented and test-pinned. Widths on the generic attribute means consuming key=value, which revises that. `TableOfContents` (`levels`) and `SectionBreaks` (`orientation`, `margins`) already do, but both read `TryGetAttributes().Properties` themselves for a marker paragraph rather than going through `Resolve` — a table would be the first case where an ordinary block's attribute carries more than a style name.
- **Layout** — explicit widths would presumably emit `tblLayout` fixed, as the existing width path does. Equal fixed columns and autofit look different, so this is a rendering decision.

## Non-obvious gotchas

- **`readme.md` is generated; `src/Parchment/nuget-readme.md` is hand-maintained**: every code block in the root readme is a `<!-- snippet: X -->` / `<!-- endSnippet -->` pair that MarkdownSnippets extracts from compiled, executing tests (config: `src/mdsnippets.json`, run on every push by `.github/workflows/on-push-do-docs.yml`, which auto-commits the regenerated file). A signature change breaks the build and the readme is rewritten, so those blocks cannot drift. **`nuget-readme.md` contains no snippet markers**, so its fences compile against nothing and rot silently — and it is the nuget.org landing page (`Parchment.csproj` `PackageReadmeFile`). Every sample in it had drifted before being corrected by hand. It is deliberately not snippet-ified: MarkdownSnippets appends root-relative `snippet source` links, which resolve on GitHub but 404 on nuget.org. **Any public signature change needs a manual check of `nuget-readme.md`.**

- **`mdsnippets.json` sets `ValidateContent: true`**, which rejects a configured list of informal words across **every** markdown file in the tree — including scratch files that were never checked in. A stray note dropped in the repo root will fail the build of `Parchment.Tests` with a `Content validation: Invalid word detected` error pointing at a line in that file. The rejected list is printed in full in the error message.

- **Reading a `StyleSet` rewrites the styles part.** `StyleSet.Read` touches `StyleDefinitionsPart.Styles`, which materializes that part's DOM — and OpenXml then re-serialises it on save in its own attribute order, so the output no longer matches the template byte for byte. The content is unchanged and Word does not care, but snapshots move. The docx flow wraps the read in a `Lazy<StyleSet>` so it only materializes when a token actually asks for styles; the markdown renderer used to read it eagerly for a field nothing consumed, which is why removing that field changed a scenario baseline. The same applies to any part whose typed root is touched.

- **A package is saved by its `Dispose`, and by nothing else.** `WordprocessingDocument.Open(stream, true)` opens with `AutoSave` on, so disposing the document serialises every part whose typed root was touched and then closes the zip. An explicit `doc.Save()` ahead of that serialised each of those parts a second time for the same bytes, which was a quarter of a render and of a registration. Every site that opens a package for writing (both `Render` methods, `RegisterDocxTemplate`, `PrepareStyleSource`, `BakeStyleSource`, `WordFieldResolution.Resolve`) therefore ends its `using` block without a save. Two things have to keep holding: the stream is not read until that block has closed (`ZipTimestamps.Pin`, `MacroParts.RemoveContentTypeDefaults`, the page-number resolver and `stream.ToArray()` all run after it), and no site opens with `OpenSettings { AutoSave = false }`, which would write nothing at all. Tests: `PackageSaveTests`.

- **Generated code names every bindable member, so their use-site diagnostics land in a file the consumer cannot edit.** `UseSiteDiagnostics` reads `[Obsolete]`, `[Experimental]` and the `Requires*` attributes off each member and type as `ShapeBuilder` walks them; the ids travel on `ModelShape.SuppressedDiagnostics` into a `#pragma warning disable` at the top of the file, emitted only when non-empty so other models' output is unchanged. Obsolete-as-error (`CS0619`) cannot be suppressed, so that member is dropped from the shape instead — after its name is claimed, so a base member it hides is not bound in its place. This is one place the generator is deliberately narrower than the runtime: reflection still sees such a member, so a hand-registered template against a `[ParchmentBindable]` model passes runtime validation for it while the generated accessors have nothing to read. `GeneratorDriver.Run` never compiles the output; shapes that could break it belong in a `GeneratorDriver.Compile` test (`UseSiteDiagnosticGeneratorTests`), which builds against the real Parchment assembly and collects warnings from the generated trees.

- **Some asymmetries are constraints, not oversights.** Each of these looked like a defect, was investigated, and is deliberate — with a test pinning it, so a passing test asserting "ignored" is evidence of a decision rather than a gap:
  - `{.StyleName}` is *unreachable* on a thematic break, a table row or cell, and an html block. Markdig binds the attribute somewhere else in each case — to a `ParagraphBlock`, to the whole `Table`, or nowhere. Not implementable, so documented instead.
  - A fenced code block's language arrives as a synthesised `language-xxx` class. `MarkdownStyle.ResolveCodeBlock` skips it, or every ` ```csharp ` block would get a style called `language-csharp` that nobody defined.
  - An explicit column alignment (`|:-:|`) still applies to a styled table, while the renderer's default borders, cell margins and implicit header centring stand down. The alignment is authored intent; the defaults are supplied on the author's behalf.
  - Equal table columns cannot be stated: equal dash counts are indistinguishable from the conventional `| --- | --- |`, so the heuristic reads them as "no opinion". See "Equal table column widths are deliberately inexpressible" above.
  - A render attribute on a static member stays a no-op. The generator reports it as `PARCH019`; registration at runtime reports nothing (`TemplateStore` logs only the two "Registered … template" information lines), and the attribute maps still walk instance members only.

- **Tokens straddling run boundaries**: Word splits text into multiple `<w:r>` when formatting changes, proofing markers fire, or smart-quote autocorrect runs. `{{ customer.name }}` can land across N runs. Scanner uses `paragraph.InnerText` + `RunMap` (offset → `<w:t>`) so substitutions land correctly. Formatting of the **first run** containing the opening `{{` wins for the entire substitution.

- **PascalCase tokens**: Parchment liquid uses PascalCase (`{{ Customer.Name }}`), and a model member is matched without regard to case. Fluid's member access is ordinal by default, so `SharedFluid.BuildOptions` sets `MemberAccessStrategy.IgnoreCasing` — before the first accessor is registered, because the strategy chooses the comparer for its map in `Register`. Without it the render disagrees with the four validators and the root-keyed attribute maps, all of which compare member names `OrdinalIgnoreCase`: a token in another case registers, then reads nothing. Loop variables and liquid's own `size` / `first` / `last` are not model members and keep their exact spelling (see "Validation topology"). Tests: `MemberCaseTests`. No snake-case translation — an earlier `MemberNameStrategies.SnakeCase` attempt was abandoned (API doesn't exist in Fluid 2.15).

- **Method-call syntax (`{{ Customer.FullName() }}`) fails at registration, not silently at render**: Fluid's `AllowFunctions` stays off — Parchment's binding model is data, not behaviour. `FluidParser.TryParse` returns false; runtime surfaces `ParchmentRegistrationException`, SG surfaces `PARCH006` in both flows — for markdown from the whole-file parse, for docx per token (`Token.ParseError`, set by the SG `TokenScanner.ParseSubstitution`). A block tag whose expression fails to parse is `PARCH003` instead. Workaround: expose a computed property.

- **Indexer syntax with a string literal (`{{ Customer['FullName'] }}`) is validated the same as dotted access**: Fluid treats both as the same member resolution at render time. That holds for an object only: on an array Fluid reads a bracketed string as an index, so `{{ Lines['size'] }}` validates like `Lines.size` but renders the first element — the path collectors flatten the two notations, so the validators cannot tell them apart. The three path collectors (`Liquid/IdentifierVisitor.cs`, `Parchment.SourceGenerator/IdentifierVisitor.cs`, `MarkdownValidator.ExpressionPathCollector`) extract the literal from `IndexerSegment { Expression: LiteralExpression { Value.Type: FluidValues.String } }` and treat it as `IdentifierSegment`. Shared extractor: `Liquid/IdentifierVisitor.TryGetStaticName` (runtime) and `Parchment.SourceGenerator/SegmentNames.TryGetStaticName` (SG); mirror when tightening. Side effect: Excelsior / Format / StringList dispatch also accepts indexer notation. Tests: `ReferenceValidatorTests.Indexer*`, `ParchmentTemplateGeneratorTests.*IndexerStringLiteral*`.

- **Any other indexer (`{{ Tags[0] }}`, `{{ Lines[i].Name }}`) stays in the path as an index segment**: `IdentifierPath.Index` (runtime) ↔ `SegmentNames.Index` (SG), emitted by the same two extractors. Ending the path at the indexer instead reads `Tags[0]` as `Tags`, and the token is then taken for the member it indexes into: the whole bullet list, the whole `[ExcelsiorTable]`, the whole `[Html]` value, an editable control. Two things depend on the segment. A path holding one is never that member — no key of the root-keyed attribute maps has a bracket in it, and no `MemberEntry` is spelled that way — so the token goes to Fluid as an ordinary value, and a loop over `Budgets[0].Notes` is not the editable collection `Budgets`. The markdown flow's two reads of the source text (`MarkdownExcelsiorTables.GuardUnrenderableToken`, `ValidateMarkdownExcelsiorTokens`) skip a path followed by `[` for the same reason. And the four validators step through it: on an array with a known element type the walk continues in the element, so `{{ Rows[0].Missing }}` is rejected and `{% for line in Groups[0] %}` types `line` from the element; on anything else (a dictionary key, a member picked by name at render, a string) the rest of the path is unknown, so it is accepted unchecked and a loop variable sourced there is untyped (`LiquidMembers.TryResolveIndex` ↔ `ShapeResolver.TryResolve` returning `ShapeResolver.Untyped`). Liquid has no index into a string, so `{{ Body[0] }}` renders nothing in either flow. Identifiers inside the brackets are not validated: Fluid's `AstVisitor` does not descend into an `IndexerSegment`. Tests: `IndexerTests` (runtime) and `IndexerGeneratorTests` (SG) run the same paths.

- **`ScopeTreeRunner.ProcessLoopAsync` attaches each iteration's clones to a scratch `Body` before running the nested scope tree**. Without this, nested `{% for %}`/`{% if %}` silently no-op: `open.Parent` returns null on a detached clone, `CaptureBetween` captures nothing, the inner block-tag text lands as literal `{% for ... %}`. Reverting to `parent.InsertAfter(clone, insertAnchor)` *before* the nested run breaks nested loops in a way only `LoopTests.NestedLoop` catches.

- **`ScopeTreeRunner.ProcessIfAsync` keeps the chosen branch positionally, not via anchors**: static paragraphs and tables inside a branch have no anchor bookmarks and no scope-tree nodes (`TokenScanner.Scan` skips token-free paragraphs), so the runner captures the chosen branch's physical range — everything between its tag paragraph (`IfBranch.TagAnchorName` / `IfNode.ElseAnchorName`) and the next boundary tag (`{% elsif %}` / `{% else %}` / `{% endif %}`). An anchor-derived keep-set silently drops static/table content in the chosen branch; `ConditionalTests.StaticParagraphInChosenBranchIsKept` and `TableInsideChosenBranchIsKeptAndSubstituted` guard against regressing. Same reason `IfNode.ElseAnchorName` (not `ElseBody.Count`) signals an else branch: a static-only else has an empty body but still owns a physical range.

- **Cancellation is checked inside the work, and is never wrapped**: the token passed to `Render` is checked on entry (before the template is resolved or the model read), by `ScopeTreeRunner` per loop iteration and per token, and at the markdown flow's phase boundaries — after the liquid render, per node of the Markdig walk (`RendererBase.ObjectWriteBefore`, subscribed in `MarkdownRendering.Render` only when the token can be cancelled), and before the save. Fluid 2.40 has no cancellation of its own, so the liquid render of a markdown template runs to its end before the token is looked at. An `OperationCanceledException` reaches the caller as thrown: any `catch (Exception)` that wraps into `ParchmentRenderException` needs a `catch (OperationCanceledException)` rethrow ahead of it, as `ScopeTreeRunner.EvaluateTokenAsync` has. Tests: `CancellationTests`.

- **A loop iteration or a chosen branch indexes a paragraph by its direct children, unless the tree says to look further**: `ScopeTreeRunner.CollectAnchors` runs for every element of every iteration, so for a paragraph it reads the anchor off the direct children and stops, and only walks the whole subtree of a table or any other element. A paragraph anchoring a text box carries more anchors below it, on the box's own paragraphs. `ScopeTreeBuilder` marks a block that holds such a paragraph between its tags (`LoopNode.NestedAnchors` / `IfNode.NestedAnchors`, from the ancestors of the token-bearing paragraphs at registration) and the runner walks below a paragraph for those blocks alone. Dropping the flag, or indexing a block's elements some other way without it, leaves the tokens and block tags in the box as literal text while the same paragraph outside any block renders, because the root map (`Anchors.BuildMap`) walks every paragraph. Tests: `TextBoxInBlockTests`.

- **Produced content is renumbered through `BookmarkIds`, one per render** (`Word/BookmarkIds.cs`): a bookmark's `w:id` has to be unique across the whole document, and nothing that produces content can see which ids are taken — OpenXmlHtml restarts at 1 for every conversion, the markdown renderer for every render. So each produced fragment is renumbered from a running counter as it is produced (`ScopeTreeRunner.RenderTokenValue` and `QueueEditableHtml`, `MarkdownRendering.Render`, `MarkdownTokenBlocks.Insert`, `MarkdownExcelsiorTables.Replace`), walking only the fragment. Names are never touched, and links and `PAGEREF` fields refer to names, so renumbering is safe. The counter is seeded at registration with the highest id in the template — every part in the docx flow, every part but the replaced body in the markdown flow — *after* anchors are inserted, so nothing numbered from it shares an id with an anchor. `Anchors.StripAll` does not depend on that: it takes an anchor's start and the next `w:bookmarkEnd` with that id among the same paragraph's children, never an end matched by id alone, because caller code can add a bookmark with any id anywhere in the part. The table of contents draws its `_Toc` ids from the same counter instead of walking the body for a free one, which holds only while everything that joins the body goes through `BookmarkIds` — a new path that inserts produced elements has to do the same. A `MutateToken` produces no fragment, it edits its host in place, so `ScopeTreeRunner` notes the markers the host holds before the delegate runs (`BookmarkIds.Markers`) and renumbers the pairs added beyond them (`RenumberAdded`). A marker the delegate puts outside its host, or a bookmark with only one end inside it, keeps the id the caller wrote. Not covered: a loop iteration or a paragraph split clones a template bookmark with its id *and* its name. Tests: `BookmarkIdTests`.

- **The links of a part are indexed, and the index has to be told when a part is handed out** (`Word/RelationshipIds.cs`): a link shares the relationship its part already has to the same target and otherwise takes `rIdLink{n}` one past the highest, and reading the part for each link made a document of distinct links quadratic. So `RelationshipIds` keeps, per part of the package a render works on, the targets and the highest counter, in a `ConditionalWeakTable` keyed by the package — a render owns its package, so nothing is shared between renders. OpenXmlHtml, Excelsior and `OpenXmlToken` / `MutateToken` delegates add relationships to the same parts on their own, which is why `RelationshipIds.Forget` is called before each of them runs (`WordNumberingState.ConvertHtml`, `LinkInlineRenderer.WriteImage`, `ExcelsiorTableBridge.BuildTable`, `ScopeTreeRunner.Produce` and its mutations, `MarkdownTokenBlocks.Insert`) and before `PartRelationships.Complete` takes relationships away; the next link then checks the part against what the index saw and reads what was added. A new call into code that is handed a part, and any new place that removes a relationship, needs the same call, or a later link is given an id that is taken or misses a relationship it would have shared. Every hyperlink relationship Parchment adds goes through `TryHyperlink` or `Hyperlink`, which keep the index current themselves. Tests: `LinkRelationshipTests`.

- **A bookmark name for an id comes from `BookmarkNames`, one per render** (`Word/BookmarkNames.cs`, reached as `BookmarkIds.Names`): `MarkdownBookmark.Sanitize` folds an id into a legal name and is not injective (`a-b` and `a_b`, ids that differ past 40 characters, ids that differ by case, which Word ignores), so the block that carries an id (`Define`) and everything that refers to it (`For`: `LinkInlineRenderer`, `ExcelsiorInternalLinks`) ask the map by id and never call `Sanitize` themselves. A name is settled at the first mention of its id, link or block, because a link can precede its target; a collision takes a `_2`, `_3` suffix inside the 40 characters. A repeated id (a heading in a loop) keeps only its first bookmark. `WordBookmarkAllocator` claims its `_Toc` names through `Reserve`. Not covered: names the html converter writes for an `id` attribute, and names a docx template or style source was authored with, are not registered, so those can still repeat. Tests: `BookmarkNameTests`.

- **A copy of template content is renumbered through `CloneIds`, one per render** (`Word/CloneIds.cs`): a `{% for %}` clones its body per item, and `ParagraphSplicer` clones a paragraph to cut it around a token, so each copy arrives with the ids of its source. A drawing's `wp:docPr` id, a content control's `w:id` and a tracked change's `w:id` have to be unique and nothing refers to them. The first copy of a loop body keeps the template's and each later one is renumbered as it is made (`ScopeTreeRunner.ProcessLoopAsync`, `RenderEditableCollection`); the after half of a split or an inline splice is renumbered where it still shares an id with the before half (`RenumberShared` — a drawing lands in one half only and keeps its id). `TemplateIds` reads every part at registration for where to start, and `CloneIds.For` returns null for a template with none of these ids, so most renders never walk a copy. A loop asks `CloneIds.Holds` once of its body and hands the answer to the runner for its iterations. Drawings and tracked changes count up from the template's highest. Content controls count *down* from its lowest, or from zero, because `EditableState` numbers the controls an editable field creates upwards from one in the same id space — the two have to stay apart if either changes. A new place that clones template content has to renumber the same way. Not covered: a marker that is half of a pair (a template bookmark, a moved or customXml range, an editable range), the run properties `EditableSplicer` copies when it splits a run, the section `SectionBreaks` copies per `[SECTION]`, and a clash with an id produced content brings along (OpenXmlHtml numbers an image's `wp:docPr` by its own count). Tests: `CloneIdTests`.

- **A comment keeps its first anchors** (`Word/CommentAnchors.cs`): a comment's range start, range end and reference carry the id of the comment itself, so a copy cannot be renumbered, and one comment has one range. `ParagraphSplicer` places the two ends of a range by position, as it does run content, so a split leaves the start with the text before the token and the end with the text after it. A loop is dealt with afterwards: `CommentAnchors.KeepFirst` runs once per part beside `Anchors.StripAll` and removes every repeat of a start, an end or a reference in document order. Afterwards, and not on the clone, because the copy that reaches the output first is not always the first iteration — its `{% if %}` can leave the commented paragraph out. It runs only for a template that anchors a comment (`TemplateIds.HoldsComments`), and has no work in a part without tokens, where nothing is copied.

- **Markdown lists and html lists are numbered into one part by two allocators** (`Word/WordNumberingState.cs`): a `w:numId` and a `w:abstractNumId` each have to be unique in the numbering part, and `OpenXmlValidator` reports a repeated `w:abstractNumId` but not two `w:num` sharing a `w:numId` — Word draws both lists from the first. Parchment numbers markdown lists, string lists and the list filters from counters it reads off the part once per render; OpenXmlHtml numbers the lists in the html it converts by reading the part itself and writing its definitions straight into it. So every conversion that can hold a list goes through `WordNumberingState.ConvertHtml` (`ScopeTreeRunner.RenderTokenValue` and `QueueEditableHtml`, `MarkdownTokenBlocks.Render`, `HtmlBlockRenderer`), and one that leaves the part with a new last `w:num` has the counters read again before the next definition is created. Html holding no list costs no read, and a render that converts no html still reads the part once however many lists it has. `LinkInlineRenderer.WriteImage` converts a lone `<img>`, which cannot hold a list, and goes the same way for the session's sake; an Excelsior html column goes through `WordHtmlConverter.ToParagraphs`, which writes list markers as text and no definitions. Any other new `WordHtmlConverter.ToElements` call has to go through `ConvertHtml`. In the other direction, OpenXmlHtml without an `HtmlNumberingSession` reads the part on every conversion, which made N html blocks cost 1 + 2 + ... + N reads, so every conversion is handed the render's session. With one it carries its own next id and reads the part again only when the part no longer ends with the element the session left there — which says where the last definition was written, not whether one was — so `GetHtmlSession` hands out a new session, keeping only `BulletAbstractNumId`, whenever an id has been taken since the last one was handed out. A session also shares one bullet definition between the conversions it is passed to. The docx flow's html tokens have always shared theirs; html met on the markdown side (an html block, an image, a token value in a markdown template) never has, each `<ul>` block writing a definition of its own, so the `ConvertHtml(html, imagePolicies, headingOffset)` overload those call sites use withholds `BulletAbstractNumId` for the call and puts it back after — sharing it there would change the bytes of every document with two such blocks. `MarkdownTokenBlocks` drops the session's ids (`ForgetHtmlIds`) after an `OpenXmlToken`, which was handed the main part and can have written definitions where a session does not look. Not covered: an `OpenXmlToken` or `MutateToken` that writes numbering definitions through `IOpenXmlContext.MainPart` itself instead of asking for them with `CreateBulletNumbering` / `CreateOrderedNumbering`. Tests: `NumberingIdTests`.

- **The markdown walk says which whole-document passes can be skipped** (`OpenXmlMarkdownRenderer.MayHoldBookmarks` / `MayHoldSections`): `MarkdownRendering.Render` only runs `BookmarkIds.Renumber` over what it produced when the walk wrote a bookmark or converted html, and `RegisteredMarkdownTemplate.Render` only runs `SectionBreaks.Apply` when the walk wrote a `[SECTION]` marker, converted an html block, or a parked token or `[ExcelsiorTable]` placeholder was registered (caller code, which can return any paragraph). A render with none of those walks neither. This holds only while every writer sets its flag: `AddBookmarkStart`, `SectionBreaks.TryWrite`, and the two `WordHtmlConverter.ToElements` call sites (`HtmlBlockRenderer`, and `LinkInlineRenderer.WriteImage` for bookmarks). A new renderer that emits a `w:bookmarkStart`, a paragraph carrying a `w:sectPr`, or content it did not build itself has to set the matching flag, or the pass is skipped and the ids collide or the marker is left as a bare `w:sectPr`. The flags are decided by the walk rather than read off the template source because a marker inside a loop, a conditional, a `| markdown` value or a `MarkdownToken` only exists once liquid has rendered. `TableOfContents.IsMarker` and `SectionBreaks.IsMarker` run for every paragraph, so both turn away a paragraph whose first inline is not a literal opening with `[` before building its text; a leading literal that is all whitespace falls through to the full comparison, which trims. Tests: `MarkerDetectionTests`, `BookmarkTests.IdsAreUniqueAcrossMarkdownAndHtmlBookmarks`. Benchmark: `MarkdownMarkerFreeBenchmarks`.

- **Typed child-element setters are kept out of the markdown walk where the properties element is new** (`ListBlockRenderer`, `TableRenderer`, `EmphasisInlineRenderer`, `LinkInlineRenderer`, `HeadingBlockRenderer`, `QuoteBlockRenderer`, `OpenXmlMarkdownRenderer.FlushParagraph`): `paragraphProperties.NumberingProperties = ...`, `runProperties.Bold = ...` and the like go through the SDK's `SetElement`, which finds the schema position by comparing qualified names it boxes one at a time, at 0.5 to 12 KB a call. That was most of what a render of lists, emphasis or an aligned table allocated. A `w:pPr`, `w:rPr` or `w:tcPr` that does not exist yet is therefore built through the children constructor (or `Append`), and put into its empty or properties-less parent with `Append` / `PrependChild`. **Those append in the order written, so the order in the source is the schema sequence and is kept by hand**: `pStyle`, `numPr`, `ind`, `contextualSpacing`, `jc` in a `w:pPr`; `rStyle`, `rFonts`, `b`, `i`, `strike`, `highlight`, `u`, `vertAlign` in a `w:rPr`; `tcW`, `gridSpan` in a `w:tcPr`. A wrong order is invalid markup that Word may repair or refuse, and no compiler notices. Where the properties may already hold children - emphasis reaching a run a second time, a link or a header cell around formatted text, a cell built by the general path - the typed setter stays, because it is the one thing that knows the position. `HeadingBlockRenderer.Write` prepends its `w:pStyle`, so the properties a container hands it must not carry one. A new element added to one of these shapes needs its place in the sequence checked and a case in `PropertySequenceTests`, which pins each shape child by child and validates a document holding all of them.

- **`SettingsProtection` must respect the CT_Settings sequence**: `w:settings` is a strict xsd:sequence — appending `w:documentProtection` at the end produces a file Word "repairs". Insertion goes before the first child not in the preceding-types set. Two naming traps when touching that set: the settings-level `w:trackChanges` element is SDK class `TrackRevisions` (NOT `TrackChanges`, which doesn't exist), and `RemoveDateAndTime` sits between `RemovePersonalInformation` and `DoNotDisplayPageBoundaries`. `EditableFieldTests.OutputValidates` runs `OpenXmlValidator` over the output — it catches ordering mistakes.

- **`EditableSplicer` exists because `ParagraphSplicer` duplicates zero-width elements**: the clone-and-trim approach distributes paragraph-level elements with no text (bookmarks, `permStart`/`permEnd`, emptied sdt shells) into BOTH halves (only run content — a tab, a break, a drawing — and the two ends of a comment range are placed by position relative to the token) — harmless for anchor bookmarks (StripAll removes them), fatal for editable fields (duplicate perm ids, stray control shells) when a paragraph hosts more than one. `EditableSplicer` splits runs at exact token boundaries instead. It inserts beside the run owning the token's first character, in that run's own parent, so a token inside an inline wrapper (`w:hyperlink`, an author's `w:sdt`, `w:ins` / `w:moveTo`, `w:smartTag`, `w:fldSimple`, `w:dir` / `w:bdo`) keeps its place inside the wrapper — all of them take `w:sdt` and the perm-range markers as children — and a token straddling a wrapper's edge lands on the side it starts on. Inserting at paragraph level instead moves the control past the wrapper's remaining text. The one wrapper that cannot take it is an author's content control holding a single value (`w:text`, `w:date`, `w:dropDownList`, `w:comboBox`, `w14:checkbox`, `w:picture`): schema-valid, but Word reports the file as corrupt, so `EditableTokenValidator` rejects the token at registration and the generator reports `PARCH016` (`DocxArchiveReader.IsValueControl` mirrors `EditableTokenValidator.ValueControlKind`; change both together). Don't "simplify" editable splicing back onto `ParagraphSplicer.SpliceInline`; `EditableFieldTests.TwoEditableFieldsInOneParagraph` and `TokenStraddlingRunsSplicesCorrectly` guard it.

- **SG-side `EditableFieldKind` / `ProtectionMode` are copies matched by member name**: the generator can't reference Parchment.dll, so emission writes `global::Parchment.Generated.EditableFieldKind.{name}` / `global::Parchment.ProtectionMode.{name}` from its own enum's `ToString()`. Renaming or reordering members on either side silently breaks generated code or protection pass-through — change both in the same PR (same class of trap as the `[ExcelsiorTable]` FQN-string match). The attribute argument is any int the author cared to cast, so a value the SG-side enum does not name has no `ToString()` but its digits: it is reported as `PARCH036` and written as `(global::Parchment.ProtectionMode)(n)`, never by name.
- **Generated code is compiled with the consumer's `LangVersion`, and C# 14 is the only floor supported**: emission may use anything up to C# 14 and is not kept compatible with older versions. A project below that gets `PARCH038` on each model and nothing else — no validation, no emitted source — decided from the parse options of the model's own tree and carried on `TargetInfo.UnsupportedLanguageVersion`. The check has to stay ahead of everything in `Process` / `ProcessBindable`: anything emitted beside it is compiled at the old version and buries the one useful diagnostic under compiler errors in a `.g.cs` file. `LanguageVersionGeneratorTests` holds both halves.

- **`OpenXmlMarkdownRenderer` is not thread-safe** — one instance per render. The `Stack<ContainerState>` and `ObjectRenderers` are mutable. The `RegisteredTemplate` (cached canonical bytes + scope tree) IS immutable — concurrent renders work, each gets its own renderer.

- **A markdown table stops at Word's 63 columns** (`TableRenderer.MaxColumns`): Word does not open a document holding a wider table, and neither `OpenXmlValidator` nor Morph objects to one, so the renderer refuses it. The width is the widest row's rather than `ColumnDefinitions.Count` — Markdig pads every row of a pipe table out to its widest while the definitions stay at the separator row's count. The renderer sees neither the template name nor, in the docx flow, the token, so it throws the internal `TableColumnLimitException` and both callers of `MarkdownRendering.Render` (`RegisteredMarkdownTemplate.Render`, `ScopeTreeRunner.RenderTokenValue`) rethrow it as a `ParchmentRenderException`; a third caller has to do the same. The other two table producers are not checked here: OpenXmlHtml drops the cells of an html table past column 63, and Excelsior writes an `[ExcelsiorTable]` at whatever width its element type has. Tests: `TableRendererTests.TableOverTheColumnLimitIsRejected`, `FormatAttributeTests.MarkdownTableOverTheColumnLimit*`.

- **`build.yml` font validation** — every TTF/OTF in `src/Fonts/` is loaded through `PrivateFontCollection` BEFORE copy to `%WINDIR%\Fonts`, catching Git CRLF corruption upfront. When adding a font, mark it binary in `.gitattributes` (already present for `*.ttf`, `*.otf`).

- **`ParchmentModel` is a separate project** (not `Model`) to avoid clashes with common test fixture names in IDE autocomplete.

- **Excelsior dispatch bypasses Fluid, deliberately**: `ExcelsiorTableBridge` walks the CLR model directly via cached `Func<object, object?>` getter chains. Routing through Fluid would erase `IEnumerable<T>` (`ArrayValue.ToObjectValue()` returns `FluidValue[]`) — `new WordTableBuilder<T>(data)` needs the typed enumerable. This is why `ScopeTreeRunner` takes `rootModel` as a separate ctor param. Removing it breaks Excelsior on the first filtered or loop-nested token.

- **Parchment is binary-coupled to Excelsior's `WordTableBuilder` constructor**: `ExcelsiorTableBridge.BuildTable<T>` calls `new WordTableBuilder<T>(data).Build(mainPart)` in *compiled* IL (only the generic-method dispatch is reflection). So an Excelsior release that changes `WordTableBuilder`'s ctor signature — **even adding an optional parameter** (which the compiler bakes into the call site, changing the binary arity) — breaks the already-compiled Parchment: consumers hit `MissingMethodException: WordTableBuilder..ctor(...)` at render time. Bumping the `Excelsior` `PackageReference` is **not** enough — Parchment must be rebuilt and republished against the new Excelsior. Conversely, additive Excelsior changes (new fluent methods like `BodyStyle`/`BodyParagraphStyle`) are safe and need no Parchment rebuild. Symptom seen in the wild: every `[ExcelsiorTable]` report throwing while loop-built tables (which don't go through the bridge) render fine.

- **Per-branch visited set in `AccessorEmission.WalkForMaps`**: cycle prevention uses a `HashSet` with `Add` on descend / `Remove` on return. Same type at unrelated paths (e.g. `Order.Buyer.Addresses` + `Order.Seller.Addresses`) still visits both; a self-reference (`Node.Next` → `Node`) is pruned. A global no-removal visited set silently drops the second sibling branch.
- **`WalkForMaps` descends only into types in `TypesReachingMap`**: the per-branch visited set makes the walk enumerate every acyclic path, which is factorial on a densely connected model (ten fully connected types with no marked member: 23-34 s and 56 GB per generator run). `TypesReachingMap` is the set of types declaring a member the walk claims (`[ExcelsiorTable]`, string list, `[Html]` / `[Markdown]`, `[EditableField]`) or leading to one, grown to a fixed point so a cycle cannot settle a type early. It must stay a superset of what the walk can add an entry from: any new map member has to be added to `HasMemberReachingMap` too, or its entries vanish wherever no other marker shares the branch. Where entries are real the walk and the emitted arrays still grow one entry per path.

- **SG `[ExcelsiorTable]` detection matches by FQN string** (`"global::Parchment.ExcelsiorTableAttribute"` in `ShapeBuilder.HasExcelsiorTableAttribute`) — SG can't `typeof()` it. Renaming/moving the attribute silently breaks `PARCH007`/`PARCH008` until the literal is updated.

- **Excelsior runtime and SG validators must stay in lockstep**: `ExcelsiorTokenValidator` (runtime) and `ValidateExcelsiorToken` + `ShapeResolver.TryResolveMappedMember` (SG) enforce the same two rules — solo-in-paragraph and plain-member-access. Solo has one definition, `TokenScan.IsSolo` (the only token site, whitespace around it ignored), which the runtime validator, `ScopeTreeRunner` (structural swap, string-list auto-bullet, editable html) and the SG's `TokenScanner` (`Token.HasOtherContent` on a substitution) all call. Runtime checks Fluid AST directly; SG piggybacks on `Token.IsPlainIdentifier` from `TokenScanner.IsPlainMemberAccess`. Tighten both in the same PR.

- **Names in generated code go through `Identifiers`; hint names through `HintNames`**: `ISymbol.Name` is the name without the `@` a keyword needs, which is right for a template path and for a binding-table key and wrong as code. Every member, type declaration and `Configure` target is emitted through `Identifiers.Escape` / `EscapeDeclaration` (type references come from `SymbolDisplayFormat.FullyQualifiedFormat`, which escapes on its own). A hint name is flattened from namespace, enclosing types and type name, which is neither injective (`A_B.C` / `A.B_C`) nor case-safe (`Letter` / `letter`), and a duplicate throws out of `AddSource` and drops the output of every model in the project. `HintNames.Disambiguate` numbers the colliding targets by sorted fully qualified name, so the result does not depend on input order; the bindable flow combines each target with that (normally empty) list rather than with the collected targets, which keeps per-target caching. Known gap: a type named `var` in the model's namespace captures the `var` in the emitted setters. Tests: `GeneratedIdentifierTests` (SG) and `KeywordIdentifierTests` (runtime, where the shapes are compiled for real).

- **`MemberEntry.IsExcelsiorTable` must stay primitive** — it's a `bool` on a `sealed record` flowing through the incremental generator pipeline; equality is structural. Adding a `bool` was safe; adding `List<T>`, an `ISymbol` reference, or any mutable field defeats cacheability and forces ShapeBuilder to re-run on every compilation.

- **A `TypeEntry` is built once per compilation and shared by every model reaching the type** — `ShapeBuilder.sharedEntries`, a `ConditionalWeakTable` keyed on the `Compilation`, so the symbols it holds die with their compilation and never enter the pipeline (a static dictionary keyed on symbols would pin every compilation the IDE ever made). Each model still does its own walk, because the order of `ModelShape.Types` is the order that walk meets the types in; only the per-type member read is shared. Without it 50 models over one 300-type graph spent 3 s and 616 MB on every edit, against 0.12 s and 25 MB. The constraint: `BuildEntry` may read `root` only where it also sets `dependsOnRoot`, which keeps that entry out of the table. Two places do today — a member that is not public or internal taking a name a base type binds (hidden only for a model that can see it), and `[ExcelsiorTable(Configure = ...)]` (the forwarder is named after the model). A new rule that asks what the model can access, or names the model, and does not set the flag hands one model's answer to all the others. The key compares with `SymbolEqualityComparer.IncludeNullability`, since `Box<string?>` and `Box<string>` print alike but their members differ in nullability. `SharedShapeGeneratorTests` generates models together and alone and compares the files.
- **SG diagnostics must be reported at a source location** — every descriptor is reported at the model's attribute. `TargetInfo` carries that as the primitive `EquatableLocation`; `LocatedTarget` pairs it with the attribute's `SyntaxTree` and `EquatableLocation.ToLocation(tree)` rebuilds `Location.Create(tree, span)`. A path-only location (`Location.Create(path, span, lineSpan)`) is an external-file location that `#pragma warning disable`, `[SuppressMessage]` and per-file `.editorconfig` severities never match. The tree compares by reference and is the one exception to the primitive-only rule: a compilation reuses the tree instance of every file an edit did not touch, so the cache only misses when the model's own file changes. Do not swap it for `CompilationProvider`, which changes on every edit.

- **Package dep direction is Parchment → Excelsior, hard**. The `[ExcelsiorTable]` attribute deliberately lives in Parchment, not Excelsior. Moving it to Excelsior would invert the dep: every Excel-only Excelsior consumer would pull Parchment, and every Parchment user would have to reference an attribute-only stub package. Don't.

- **Every library `await` carries `ConfigureAwait(false)`**: a caller blocking on a render from a single-threaded synchronization context (WPF, WinForms, classic ASP.NET) deadlocks on any await that resumes on the captured context. CA2007 is an error for `src/Parchment` and `src/Parchment.Morph` through the `.editorconfig` in each project folder; the root `.editorconfig` cannot hold the rule because ProjectDefaults overwrites that file on every build. `await using` needs the block form over `stream.ConfigureAwait(false)`. Regression: `SynchronizationContextTests`.
- **SG markdown reads via `AdditionalText.GetText`, not `File.ReadAllText`**: RS1035 bans `File.*` in analyzers. `ParchmentTemplateGenerator.ReadMarkdown` calls `text.GetText(cancel)` and treats null as a read error. Test harness's `PathAdditionalText.GetText` returns `SourceText` for `.md`/`.markdown` but `null` for `.docx` (docx branch reads the bytes off `text.Path`). Failure mode is `PARCH006` "AdditionalText returned no SourceText" — loud, not silent.

- **The SG's Roslyn references are tied to its package folder names and do not follow a package bump**: the SDK hands a compiler the newest `analyzers/dotnet/roslynX.Y` folder that is not newer than the compiler, and a compiler refuses an analyzer that references a newer `Microsoft.CodeAnalysis` than its own — with warning CS9057, not an error, so the generator is skipped, the build passes, and every model throws "has no pre-compiled Parchment accessors" at first render. `Parchment.SourceGenerator.csproj` therefore overrides the central version per target framework (`netstandard2.0` → 5.0.0 for `roslyn5.0`, `net10.0` → 5.3.0 for `roslyn5.3`). The central `Microsoft.CodeAnalysis.CSharp` version only picks the compiler the SG tests host the generator in, and is free to move. Raising an override means renaming its folder, which drops every compiler older than the new name; `roslyn5.0` is the compiler of the first .NET 10 SDK. A build on the current SDK cannot notice a mismatch, since it is given the newest folder and satisfies any reference, so `AnalyzerPackagingTests` in `IntegrationTests` reads the references of the packed assemblies and compares them with their folder.

- **Public fields are bindable at every depth**: `ShapeBuilder.TryGetMemberType` surfaces public fields alongside properties, so `AccessorEmission` emits a `DelegateAccessor` for each and their types recurse into the shape. Without that, top-level field access still works (`TemplateContext(model, ..., allowModelMembers: true)` reflects on the root instance) but nested-via-field access (`{{ Outer.FieldOnInner }}`) renders empty. `ModelValidator.TryResolveMember` (registration-time token validation) reads fields too.

- **Model binding limitations** — see `readme.md` → "Model binding limitations" for the user-facing list (interfaces as `TModel`, interface default impls, C# 14 extension properties, explicit interface implementations all unsupported). Implementation: runtime interface block is `GuardBindingModel` in `TemplateStore.cs` (abstract classes supported; tests in `InterfaceModelTests`). SG block is `[AttributeUsage(AttributeTargets.Class)]` on `ParchmentModelAttribute` (CS0592). For the other three, `ShapeBuilder.BuildEntry` deliberately doesn't walk `current.Interfaces` and never visits extension containers. Inheritance from a base **class** IS supported (`ReferenceValidatorTests.InheritedMember_*`, `ParchmentTemplateGeneratorTests.InheritedMember_Validates`).

- **`MarkdownValidator` binds the loop variable to the root type when source is unresolved**: in `WalkFor`, a loop whose `Source` fails (PARCH001/002) still binds `Identifier` → `target.Shape.RootTypeFullyQualifiedName` for the body walk. Intentional cascade-suppression — stops every body access (`{{ line.Description }}` etc.) from also tripping PARCH001. Skipping the body walk would stop validating nested constructs; binding to a sentinel would generate false positives. Wrong-but-optimal — keep it.
